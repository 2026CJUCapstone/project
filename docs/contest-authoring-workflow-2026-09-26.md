# 비공개 대회 패키지와 출처·검수 기록

2026-09-26 구현 기록. 로컬 합성 자료 검증이며 실제 문제 이용 허락·자원 측정·운영 등록의 증거가 아니다. 운영 배포와 등록은 하지 않았다.

## 등록 계약

- `POST /api/v1/contests/packages/import`: 관리자만 사용한다. 새 문제와 **비공개** 대회, 출처 메타데이터, 등록 영수증을 한 트랜잭션으로 저장한다. 외부 URL을 가져오거나 자산 파일을 실행하지 않는다.
- `GET /api/v1/contests/packages/{packageId}`: 등록한 관리자에게만 영수증을 반환한다. 공개 응답에는 지문·테스트·출처 증거를 넣지 않는다.
- 같은 ID와 정규화한 내용의 재요청은 기존 결과를 반환한다. 같은 ID로 내용·일정·배점·revision을 바꾸면 409다. 이후 편집은 대회 관리 화면에서 수행한다. 재시도는 관리자 편집을 덮어쓰지 않는다.
- 영수증의 `originalProblems`는 최초 연결을 보존한다. `problems`는 현재 연결이다. 일정 편집으로 대회 문제 행 ID가 바뀌어도 현재 ID를 돌려준다. 삭제한 항목은 `removed: true`와 `contestProblemId: null`로 표시하고 복구하지 않는다.
- 동시 등록은 기존 DB 실행 잠금 아래 직렬화한다. 중간 오류는 문제·대회·출처·영수증 모두 롤백한다. PostgreSQL에서의 실제 경쟁 실행은 별도 수락 조건이다.

입력은 `backend/app/models/problem_authoring.py`의 `PrivateContestPackage`가 정의한다. `packageId`, `revision`, 제목, 시간대가 있는 시작/종료 시각과 문제 배열이 필요하다. 문제당 테스트 최대 200개, 인라인 테스트 한 개의 입력+출력은 1 MB, 인라인 테스트 합계는 4 MB로 제한한다. 등록 도구·서버는 동일한 alias 정규 JSON을 세고, 프록시와 직접 API의 요청 본문은 512 KiB 이하로 제한한다. 이보다 큰 비공개 테스트는 관리자 업로드 경로에 먼저 별도로 저장하고, 패키지에는 내용 대신 SHA-256·바이트 수 참조를 넣어야 한다. 저장 참조의 존재·무결성은 대회 저장 때 다시 검사한다. 배점·일정·등급·이용 근거를 도구가 대신 결정하지 않는다. A–J 초안 묶음 생성기는 구현했지만, 미확정 값을 채운 최종 등록 파일은 아직 만들지 않았다.

## A–J 비공개 초안 묶음

`scripts/build_freshman_private_package.py --template-output config.json`은 현재 고정된 79개 초안과 출제 자산 해시가 든 설정 틀을 새 파일로 만든다. 일정, 정확한 세부 난이도, 대회·연습 배점과 태그는 `null` 또는 빈 값이므로 그대로는 실행되지 않는다. 생성기가 임시 날짜나 제안 배점을 대신 정하지 않는다. 출처 후보는 모두 `pending`, 공개는 `forbidden`, 자원 제한은 `unmeasured`로 고정한다.

운영자가 미확정 값을 명시해 채운 뒤 `scripts/build_freshman_private_package.py config.json`을 실행하면 검증만 한다. `--output-dir 새디렉터리`를 추가해야만 다음 파일을 새 경로에 만든다. 숨김 원문이 있는 묶음 출력은 owner-only 권한을 검증할 수 있는 POSIX 환경에서만 허용한다. Windows에서는 템플릿 생성과 검증만 가능하고 묶음 출력은 실패 종료한다.

- `package.json`: 정규화한 비공개 `PrivateContestPackage`. 공개 예제 26개만 inline이고 숨김 후보 53개는 모두 `stored-v1` 참조다.
- `blobs/sha256/*`: 생성기에서 다시 만든 숨김 입력·정답의 내용 주소 파일. 자동 업로드하지 않는다.
- `upload-index.json`: 각 blob의 SHA-256, 바이트 수와 상대 경로. `upload_judge_test_data.py`의 명시적 업로드 입력으로 사용할 수 있다.
- `draft-status.json`: corpus/package/asset 해시, 개수, 남은 차단 조건. `releaseReady`는 항상 `false`다.

설정은 현재 corpus와 고정 자산 목록의 해시를 함께 제시해야 한다. A–J가 하나라도 빠지거나 출처를 승인된 것처럼 바꾸거나 외부 티어 근거를 넣거나 공개 선언을 바꾸면 초안 생성기가 거절한다. `judgePolicy`도 만들지 않는다. 따라서 유효한 묶음이 만들어져도 이용 조건 검수, 지문 승인, 6언어 반복 측정과 자원 정책 승인, blob 업로드, 격리 통합 검사와 명시적 등록이 별도로 필요하다. 이 명령은 DB·API·네트워크를 사용하지 않는다.

묶음은 확인한 일반 디렉터리 아래 owner-only 임시 sibling에 완성하고 각 파일을 동기화한 뒤 최종 이름으로 바꾼다. 조상 symlink와 다른 기존 묶음은 거절한다. 같은 바이트·파일 목록·제한 권한의 완성본으로 다시 실행하면 `bundle-replayed`로 끝나며, 중간 쓰기 실패 시 최종 이름과 임시 sibling을 남기지 않는다. blob과 메타데이터 파일은 다른 계정에 권한을 주지 않으며, 이 보장을 제공하지 못하는 플랫폼에서는 출력하지 않는다.

## 안전한 등록 도구

`scripts/apply_private_contest_bundle.py 묶음디렉터리`는 A–J 생성 묶음을 **전체 단위로 오프라인 검증**한다. POSIX에서 현재 사용자 소유이고 group/other 권한이 없는 일반 디렉터리·파일만 연 파일 기술자로 고정해 읽는다. 정규 `package.json`, 정확한 A–J 순서와 pending 출처 상태, 미측정 `judgePolicy` 부재, 고정 차단 조건, 정렬된 upload index, package의 모든 stored 참조와 정확히 같은 blob 집합, 각 파일의 크기·UTF-8·SHA-256을 전부 확인한다. 링크·하드링크·추가/누락 파일·경로 우회·중복 JSON 키·느슨한 권한·읽는 중 변경은 거절한다. 기본 실행은 토큰을 읽거나 연결을 만들지 않고 안전한 해시와 개수만 출력한다.

명시적으로 승인된 비공개 등록에서는 같은 도구에 `--apply --api-base https://호스트/접두사/api/v1`을 준다. 시스템 프록시와 리디렉션·자동 재시도를 사용하지 않고, 검증한 blob을 digest 순서대로 한 번씩 업로드해 각 identity 영수증을 확인한 뒤에만 메모리에 고정한 package를 한 번 등록한다. 중간 blob 응답이 불확실하면 package 등록으로 넘어가지 않는다. 이미 저장된 내용 주소 blob은 삭제하지 않으며, 운영자가 **바뀌지 않은 동일 묶음**으로만 재개한다. 등록 응답이 불확실해도 package ID를 새로 만들지 않는다. 이 흐름은 비공개 draft를 만들 뿐 공개·검수 승인·자원 정책 승인을 수행하지 않는다.

백엔드 가상환경에서 `scripts/import_private_contest.py manifest.json`을 실행하면 **파일 검증만** 한다. 토큰을 읽거나 네트워크에 접속하지 않는다.

실제 쓰기는 별도 승인을 받은 뒤에만 `--apply --api-base https://호스트/접두사/api/v1`을 지정한다. 주소 기본값은 없다. 토큰은 `CONTEST_IMPORT_TOKEN` 환경변수에서 읽으며 명령 인자·출력에 넣지 않는다. HTTPS만 허용하고 로컬 격리 서버의 loopback HTTP만 예외다. 리디렉션과 자동 재시도는 하지 않는다.

응답이 끊기면 등록이 이미 완료됐을 수 있다. 새 ID를 만들지 말고 원래 영수증을 확인하거나 **동일 파일**로 다시 요청한다. 영수증의 ID·내용 해시·문제 연결을 확인한 뒤 라우팅 정보만 출력한다. 비밀 테스트와 서버 오류 본문은 출력하지 않는다. 이 문서의 명령 설명은 실행 승인이 아니다.

## 검수 계약과 화면

관리자 전용 API:

- `GET /api/v1/problems/{id}/authoring`
- `PUT /api/v1/problems/{id}/authoring`: 확인한 콘텐츠 지문과 새 메타데이터를 보낸다. 지문이 달라졌으면 409다.
- `POST /api/v1/problems/{id}/authoring/reviews`: 요청 ID·확인한 지문·범주·승인/반려·필수 메모를 저장한다.
- `POST /api/v1/contests/{contestId}/problems/{contestProblemId}/authoring-validations`: 저장된 대회 문제 snapshot과 등록된 기준 풀이 파일 지문이 정확히 같은 코드를 비공개 durable job으로 실행한다.
- 같은 경로의 `GET .../{jobId}`: 요청한 관리자에게만 코드·숨김 테스트·세부 출력을 제외한 판정과 자원 사용량을 보여준다. 일반 실행 기록 API에는 노출하지 않는다.
- `POST /api/v1/contests/{contestId}/rejudges/{batchId}/authoring-validations`와 같은 경로의 `GET .../{jobId}`: live 문제 대신 고정된 재채점 후보 snapshot에 기준 풀이를 실행한다. 적용·폐기·실패 후보에는 새 검증을 만들 수 없다.

대회 관리 화면의 저장된 문제 아래에 접이식 출처·검수 패널을 둔다. 출처 원본 JSON, 범주별 상태, 검수 메모와 이력을 보여준다. 외부 난이도 기록을 내부 등급으로 자동 환산하지 않는다.

검수 범주는 출처/이용 조건, 지문, 테스트 자산, 실행 자원이다. 승인은 자동이 아니며 해당 지문·테스트·정책·출처의 정확한 콘텐츠 해시에만 적용한다. 변경 후 이전 승인은 새 버전의 승인이 아니다. 반려는 과거 승인을 지우지 않고 새 이벤트로 남긴다. 요청 ID 재사용은 내용이 같을 때만 허용한다.

출처 승인은 이용 조건 확인 근거가 있어야 한다. 테스트 승인은 지정 언어 기준 풀이와 검증기·생성기·오답 자산 지문이 필요하다. 자원 승인은 테스트 묶음에 연결된 검증 정책과 지정 언어 프로필이 있어야 한다. 파일 해시만 입력하는 것으로는 공개할 수 없다. `requiredLanguages`의 각 언어에 대해 현재 snapshot·출제 지문·기준 풀이 SHA-256·정책 hash·테스트 묶음 hash와 일치하는 `accepted` 검증 증명이 있어야 한다.

성공한 검증은 queue 완료 트랜잭션 안에서 비밀 없는 증명 행을 추가한다. 증명에는 job/problem/contest/당시 contest-problem ID, snapshot·출제·소스·정책·테스트 지문, 언어와 완료 시각만 남기며 코드·입력·정답·실행 세부는 넣지 않는다. 민감 실행 payload/result가 보존 기간 뒤 삭제돼도 증명은 유지된다. 문제 내용, 기준 풀이, 정책 또는 테스트가 바뀌면 hash가 달라져 이전 증명은 자동으로 효력을 잃는다. 일정·대회 배점처럼 문제 snapshot 밖의 값만 바꾸면 같은 대회의 동일 콘텐츠 증명을 다시 사용할 수 있다.

신규 비공개 문제는 출처 추적을 생략할 수 없으며 네 범주 승인과 필수 언어별 현재 기준 풀이 통과 증명이 모두 있어야 공개 가능하다. 실패·시스템 오류·만료된 실행 receipt 또는 다른 대회/옛 snapshot 증명은 공개 근거가 아니다. 재채점 정정본도 후보별 네 범주 승인에 더해 같은 후보 snapshot의 accepted 기준 풀이 증명을 요구한다. 시작한 공개 대회가 참조하는 문제의 출처·검수 변경은 거절한다. 이미 공개돼 있던 출처 미추적 일반 문제를 대회에 그대로 편입하는 호환 경로만 유지한다. 공개 API는 출처 허락 근거와 검수 메모를 노출하지 않는다.

## 미완료와 수락 경계

- 검수 이벤트는 추가형이지만 메타데이터 변경 전체의 별도 감사 원장, 삭제된 문제의 감사 조회 화면, 공개 후 문제 개정·재채점 워크플로는 아직 없다.
- 공개된 추적 문제의 내용 변경은 기존 승인으로 통과하지 못한다. 현재는 변경본을 저장·검수하는 별도 개정 흐름이 필요하다.
- 공개 게이트 연결은 로컬 SQLite/fake runner에서 구현·검증했지만, 6언어 A–J 실측, B++ 최종 설치 기준 풀이, 전체 최대/적대적 데이터와 실제 Linux/cgroup·분리 PostgreSQL/Redis worker 수락은 별도 남은 작업이다.
- 이용 조건·현재 외부 등급·일정·J 배점/AI 이용 규칙은 임의로 승인 처리하지 않는다.
- A–J 초안 생성기의 Windows 계약 검사는 17개 통과, POSIX 출력 전용 검사 3개 skip이었다. 대신 Windows의 실제 묶음 출력 차단 검사도 통과했다. 동일 소스를 배포 서버의 네트워크 차단·읽기 전용·비운영 컨테이너에서 실행해 권한/symlink/원자 출력 19개가 통과했고 Windows 전용 차단 검사 1개만 skip했다. 이는 10문제·26 sample·53 stored hidden 참조와 해시/출력 경계를 확인한 것이며, 실제 blob 업로드·운영 등록·채점 수락은 아니다.
- 전체 묶음 검증·순차 적용 계약은 Windows에서 53개 통과/POSIX 파일시스템 1개 skip, 격리 Linux에서 54개 통과했다. Linux 검사는 네트워크 없음·읽기 전용 컨테이너와 기존 이미지에서 링크/권한/정확한 파일 집합, 89개 blob·12,718,689바이트의 reference closure, 업로드 중단/등록 순서를 모의 transport로 확인했다. 실제 API 토큰·blob 업로드·대회 등록은 사용하지 않았다.
- SQLite/모의 HTTP/브라우저 성공은 실제 운영 등록이나 Linux/PostgreSQL 수락을 대신하지 않는다. 최종 테스트 수는 구현 매트릭스와 progress 기록을 따른다.
