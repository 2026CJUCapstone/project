# B++ G/J 실패 원인 재현 및 빌드 회귀

## 결론과 남은 일

사용자 설정 문제가 아니다. 설치된 B++ 컴파일러 ref `2d596233f45973394a5d951c40b11f78171c8870`의 두 코드 생성 결함을 격리된 Linux 컨테이너에서 재현했다. **컴파일러 수정본의 Linux 수락은 아직 남아 있다.** 대회 풀이를 우회 코드로 바꾸거나 시간 제한을 늘리지 않았다.

- G: 지역 변수는 8048 bytes까지 쓰지만 함수 진입 시 2048 bytes만 예약한다. 호출 스택과 지역 배열이 겹쳐 데이터가 손상된다.
- J: 포인터 매개변수에 필요한 GC 정리 함수를 생성 결과에서 누락한다.
- 새 런타임 빌드에 두 회귀를 필수 검사로 추가했다. 기존 이미지가 이 검사를 실패하는 것도 실제로 확인했다. 기존의 결함 있는 pin으로 새 이미지를 빌드하면 이제 검사가 중단시키는 것이 의도된 결과다. 이미지 교체나 런타임 정상화가 끝났다는 의미가 아니다.

## 실제 검사

모두 기존 이미지 `sha256:7a3aa3717f2c62f60ff52f680335ebee414151136d6f836382b1b543a43c5db1`을 사용했다. 네트워크 없는 읽기 전용 컨테이너, 단일 순차 실행이며 운영 DB/큐/파일을 마운트하지 않았다. 이미지 빌드·다운로드·설치·배포·push는 없었다.

### 1. 작은 코드로 분리한 재현

[원시 보고서](evidence/bpp-diagnostic-reductions-2026-09-27.json), SHA-256 `64144d1adfc17829691e466d0593bbc69b67c8c1d8c523eb7d07858f81a9771e`.

기존 measured-v1 실행기와 자원 계측을 그대로 사용했다. 6개 소스/11개 단계 컨테이너, 정리 후 잔여 0개다.

| 검사 | 결과 |
|---|---|
| G 원본, 입력 `1 / 1000` | CPU TLE: 1,004,892 µs, 한도 1초, 출력 없음 |
| 지역 배열 초기화 | AC |
| 변수 인덱스 `+=`/`-=` | AC |
| 상수 인덱스 `+=`/`-=` | AC |
| 횟수를 제한한 배열 감소 반복 | AC |
| 최소 포인터 매개변수 함수 | CE: `std_mem__bpp_gc_root_slot_remove` 없음 |

진단용 1초는 첫 실행의 5초를 대회 정책으로 변경한 것이 아니다. 단순 배열 연산 자체보다 호출 시 지역 저장 공간이 훼손되는 경로를 확인하는 근거다.

### 2. G의 생성 코드 대조 실험

[실험 기록](evidence/bpp-g-frame-experiment-2026-09-27.json). `bpp -O1 -asm` 결과의 main 진입부는 `sub rsp, 2048`이고 실제 지역 변수 접근은 `rbp-8008`부터 `rbp-8048`까지였다.

같은 소스와 같은 입력으로 원본 실행 파일은 1초 후 종료시켰다. **main의 스택 예약 숫자만 16384로 바꾼 진단용 어셈블리**는 exit 0, 출력 `1000\n`이었다. 이 대조 실험은 원인 확인용이며 컴파일러 수정이나 채점기 기능으로 적용하지 않았다. 이 실험은 프로세스 wall timeout이며 앞 절의 보호된 cgroup CPU 계측과 구분한다.

컴파일러 저장소의 후속 commit `9859a2dc783c9346be2ab9447e1569218bcc5093`는 실제 지역 변수 크기를 반영한 프레임 예약과 `94_large_local_frame_runtime_success.bpp`를 포함한다. J와 대응하는 `dedc800fdd6586546a467e5446d04d325243706f`는 포인터 매개변수의 GC 런타임 보존을 추가한다. 저장소의 기존 사용자 변경은 읽기만 했다. 이들 수정이 포함된 고정 후보를 Linux에서 빌드·전체 회귀하기 전에는 해결 완료로 처리하지 않는다.

### 3. 필수 빌드 검사

`runtime/sandbox/verify_bpp_runtime.py`를 추가해 실제 설치된 컴파일러로 O1 컴파일→NASM→링크→실행을 검사한다.

- 큰 지역 배열을 초기화한 후 다른 함수를 호출하고, 배열 전체의 값이 유지되는지 확인한다.
- 포인터 매개변수만 사용하는 함수가 링크·실행되어 42를 출력하는지 확인한다.
- 단계별 timeout/비정상 종료/잘못된 출력을 실패로 기록하고 최종 nonzero로 종료한다.
- Dockerfile의 `USER sandboxuser` 뒤에서 필수 실행하므로 bootstrap test filter로 생략되지 않는다.
- build/updater 서명에 검사 파일을 포함해 내용 변경을 이미지 재빌드 판단에 반영한다. 현재 실행 중인 이미지에는 영향을 주지 않는다.

[실제 부정 검사 결과](evidence/bpp-build-gate-negative-2026-09-27.json): 큰 배열 검사 exit 17(데이터 불일치), 포인터 검사 동일 GC 심볼 CE. 두 실패로 도구 exit 1을 확인했다. 이는 불량 런타임 차단 증거이지 수정된 런타임 통과 증거가 아니다.

처음 검사 파일 이름에 사용한 하이픈이 구 컴파일러의 함수 심볼에 들어가 별도 NASM 오류를 일으켰다. 검사 파일의 basename을 식별자 형태로 바꾸고 다시 실행해 목표 오류 두 개를 확인했다. 실제 채점기 소스 이름은 `main.bpp`로 고정되어 있어 이 진단 도구의 파일명 문제와 구분한다.

## 전송 및 로컬 회귀

SCP는 161126-byte 자료 전송 중 16384 bytes에서 끊겼고 직접 SSH stdin도 연결이 끊겼다. 현재 Windows scp는 `-O` 옵션을 지원하지 않았다. 원인은 확정하지 않았으며 사용자 설정을 탓하거나 서버 설정을 바꾸지 않았다.

`transfer_isolated_probe.py`가 고정 테스트 파일을 8192-byte 단위로 보내 각각의 길이/해시와 최종 전체 해시를 확인하도록 했다. 대상은 소유자가 일치하는 `/tmp/webcompiler-launcher-test.*`이며 exclusive create로 기존 파일을 덮어쓰지 않는다. 이 경로로 동일 아카이브를 정상 전송했다.

최종 집중 회귀 **258 PASS, 12 플랫폼 조건 SKIP, 10 subtests PASS /9.47초**. 측정/집계/진단 입력, 전송의 경로·해시/분할 계약, 빌드 검사 단계별 오류와 빌드 연결, 기존 실행기·정책·배포·노드 검사 도구를 포함한다. Windows에서 생략된 POSIX 검사는 실제 Linux 수행으로 간주하지 않는다.

Node만 검사하는 기존 경량 도구는 B++ 설치를 의도적으로 생략하므로, 새 B++ 전용 COPY/RUN 두 줄도 정확히 식별해서 제외하도록 맞췄다. 전체 제품 Dockerfile의 필수 검사는 그대로다. 최초 새 drift 테스트가 주석 처리된 명령도 문자열로 인식하는 결함 두 개를 잡았고, 전체 줄 일치로 고친 뒤 최종 검사를 통과했다. 측정 도구는 입력 descriptor를 두 번 생성하지 않도록 정리했다. 이 마지막 정리는 로컬 회귀로 검증했으며 실제 진단 보고서는 그때 사용한 이전 스크립트 해시를 그대로 보존한다.

원시 보고서 로컬 복사와 해시 일치를 확인한 뒤 `/tmp/webcompiler-launcher-test.iGIrk4zk`(20 KiB, 실패한 전송)와 `JEwZOXfz`(1.8 MiB, 진단 자료)의 실제 경로를 검사하고 해당 테스트 복사본만 삭제했다. 로컬 자료로 다시 만들 수 있다. 관련 테스트 컨테이너는 0개였으며 기존 basic 서비스 7개 healthy를 재확인했다.

전체 Goal의 수정 런타임·6언어 반복 측정·PostgreSQL/워커 복구·나머지 구현 및 외부 승인 항목은 유지한다.
