# 자원 측정 기록·런타임 등록부 검증

작성일: 2026-09-26. 상태: 로컬 회귀 및 제한된 실제 Linux Python 연결 검사 통과. 다언어 대회 수락·운영 활성화·재채점 완료를 뜻하지 않는다.

## 구현한 범위

- `judge_metrics.py`는 감독기의 보호된 완료 기록만 집계한다. 참가자 출력이나 예외 문자열을 측정 근거로 사용하지 않는다. 기록이 없거나 형식·단계·순서·접수 지문이 다르면 거절한다.
- 일반 제출과 대회 제출에 nullable `resource_report`를 추가했다. 스키마 버전은 `20260926_judge_metrics_v15`다. 기존 행은 NULL을 유지하며 초기화를 반복해도 기존 접수·점수·정책을 바꾸지 않는다.
- 내부 기록은 정책 ID/revision/hash, 언어, 테스트 지문, 선택한 런타임·제한 프로필, 컴파일과 실행한 케이스의 보호된 CPU/wall/peak/OOM/출력량/트리 회수 여부를 보관한다. 입력·정답·소스·숨김 출력은 이 보고서에 넣지 않는다.
- 영속 저장은 기존 작업 lease/fence를 통과한 결과·점수 반영 트랜잭션 안에서 수행한다. 오래된 워커 완료, 중복 완료, 검증 실패 시 부분 저장을 방지한다. 메트릭 자체를 득점 근거로 삼지 않는다.
- 일반 제출 목록·접수 결과·대회 내 제출에는 `resourceUsage`로 컴파일 측정과 실행 합계/최대만 공개한다. 실행 CPU/wall은 실행한 케이스의 합계와 케이스 최대를 함께 제공하며, 메모리는 합계가 아닌 최대다. 실행되지 않은 단계와 구버전 미측정 제출을 0으로 꾸미지 않는다.
- 일반 제출은 기존 보관 정책을 따르며, 대회 제출 기록은 별도 보관한다. 전체 접수 payload 보관 기간이 지나도 보고서에 고정 프로필이 남는다.

관리자 전용 상세 경로는 다음과 같다. 일반 사용자에게는 거절하고 응답은 `no-store`다.

- `GET /api/v1/problems/submissions/{submission_id}/resources`
- `GET /api/v1/contests/{contest_id}/submissions/{submission_id}/resources`

화면은 컴파일 CPU/메모리와 실행 CPU/메모리를 섞지 않는다. 전체 cgroup 단계 측정이므로 감독 프로세스·런타임·tmpfs가 포함됨을 안내한다. 순수 참가자 프로세스 RSS라고 표시하지 않는다.

## 등록부와 산출물

문제 공개와 새 제출 접수에서 운영자 등록부의 언어·런타임·이미지·워커 등급·도구·실행기 해시를 정책과 대조한다. API도 동일한 승인 등록부를 읽을 수 있어야 한다. 이미 접수된 동일 요청의 재시도는 기존 영수증을 반환한다. NULL 정책의 기존 실행 방식은 유지한다.

이 대조는 **설정 승인**이지 현재 워커/이미지의 가용성 검사가 아니다. 워커는 실행 시 자신의 등급과 실제 이미지 ID를 다시 확인하지만, 실시간 준비 상태를 API에서 확인하는 기능은 남아 있다. 실제 증거 없이 등록부 항목을 만들어 운영 준비 완료로 처리하지 않았다.

Java 한글·Unicode 내부 클래스명이 기존 ASCII 산출물 검사에서 거절되던 문제도 수정했다. PAX 확장은 검증된 경로만 허용하고 시간·권한 등 부가 메타데이터는 허용하지 않는다. 경로 이탈·링크·장치 파일·예약 이름·제어문자·대소문자/정규화 충돌과 240 UTF-8 바이트 초과 경로를 거절한다. 충돌 확인은 호스트 파일을 쓰기 전에 끝난다. 로컬 Java 도구로 직접 만든 한글 내부 클래스의 컴파일→수집→복원→실행을 검증했다. 일부 Java 식별자 문자의 제한이 있으며, 모든 적법한 Java 이름을 지원한다고 주장하지 않는다.

## 실제 격리 서버 확인

사용자가 허용한 기존 배포 서버의 **격리 테스트만** 사용했다. 운영 DB·큐·대회에 연결하지 않았고 이미지 설치/pull, 서비스 교체, 운영 대회 등록, Git push는 하지 않았다.

- 기존 이미지: `sha256:d7ab3494aad02142fe7fc4abee8175283a2ce68e57cfc7bb24da034753065930`
- Python 3.12.3. 실행기: `sha256:908bb710244512ea3f655831a7aa84b4fb5d6ec370cd32e558f14944fbc0e505`
- 독립 임시 소스·디렉터리·등록부. DB 설정은 in-memory SQLite이며 테이블 초기화·큐 워커 실행 없음.
- 네트워크 차단, 읽기 전용 컨테이너. 제어기 256 MiB/0.5 CPU, 단일 단계 128 MiB/1 CPU, 단계 CPU 1초/wall 2초. 동시에 여러 채점 부하를 만들지 않았다.
- 자작 작은 Python 코드, 컴파일 1회·독립 실행 컨테이너 2개, 읽기 전용 산출물과 새 작업 공간 확인.
- 보호된 단계 보고서가 내부 채점 보고서까지 전달되고 공개 합계·최대값과 일치하는지 확인. 이는 실제 DB 워커의 영속 처리 전체 검사가 아니다.

### 앞선 v15 전체 회귀 기준선

측정·등록부·마이그레이션·산출물 테스트는 공개/관리자 분리, 위조·누락·음수/bool 지표, 케이스 순서, 접수 지문 변경, 컴파일 실패, stale 완료, 반복 완료, 트랜잭션 rollback, 초기화 2회, 레거시 NULL을 검사한다. PostgreSQL 분기는 별도 환경이 없어 명시적으로 skip하며 SQLite 결과를 PostgreSQL 검증으로 세지 않는다.

프런트 42개 파일 **221 PASS**, 타입 검사·빌드 통과. 실제 Edge의 320/768/1440px 검사 **9 PASS**(11.0초). 정책/출처/메트릭 화면의 API 응답은 모두 모의 데이터다. 스크린샷을 검토한 뒤 좁은 표 셀의 지표를 2열로 정리했다. 기존 일부 UI 테스트의 React `act` 경고는 남아 있으며 테스트 실패는 없었다.

최종 백엔드 전체는 **2443 PASS / 414 환경 skip / 8 subtests**, 278.45초다. 새 격리 SQLite DB와 명시한 B++ Windows 도구로 실행했다. 중간 실행이나 겹치는 테스트 수를 합산하지 않는다. 414개 skip은 통과로 세지 않는다.

원격 테스트 전용 임시 디렉터리는 정확한 경로를 확인한 뒤 삭제했다. 운영 파일은 삭제하지 않았다. 로컬 B++ 초기 수동 검사에서 생성한 `C:/Users/vulpo/AppData/Local/Temp/bpp-a-d-3e2c2e87a3ff435b90575931c2ff06c6`에는 재생성 가능한 A–D assembly/object/executable/빈 오류 파일 16개가 남았다. 이 환경의 삭제 정책이 거절하여 다른 방법으로 우회하지 않았다. 후속 B++ 검사는 pytest 임시 디렉터리만 사용한다.
