# 격리 cgroup 확인 기록 — 2026-09-26

사용자 승인 범위는 기존 배포 서버의 **격리 테스트만**이다. 운영 배포·DB·큐·점수판·계정·서비스 설정은 변경하지 않았다.

## 실행 범위

- Linux 6.8.0-111-generic, 기존 이미지 `sha256:d7ab3494aad02142fe7fc4abee8175283a2ce68e57cfc7bb24da034753065930` 사용. 이미지 빌드·다운로드·설치 없음.
- `scripts/verify_judge_cgroup_probe.py`로 신뢰된 Python 확인 코드만 실행. 동시 1개, 각 최대 15초, CPU 0.25, 메모리 64MiB, swap 0, PID 16, 임시 공간 4MiB, 네트워크 없음, 읽기 전용 루트, 호스트 마운트 없음, 일반 사용자, 모든 capability 제거.
- 시작 조건: 가용 RAM 2GiB·디스크 4GiB 이상. 실제 실행 전 RAM 6,664,351,744B / 디스크 4,912,263,168B, 실행 후 RAM 6,643,187,712B / 디스크 4,912,234,496B.
- 각 테스트의 부모는 자식 종료 후 잠시 살아 있어 cgroup이 사라지기 전에 CPU 합계와 memory.peak/events를 읽었다. 이는 최종 계측의 수명 조건을 확인하는 실험이지, 공격 코드에 안전한 채점 감독 프로세스 구현이 아니다.

## 관찰 결과

| 경우 | CPU usage_usec | memory.peak | oom_kill | 컨테이너 종료 코드 | Docker OOMKilled |
|---|---:|---:|---:|---:|---|
| 정상 자식 | 129,958 | 17,113,088B | 0 | 0 | false |
| 메모리 초과 자식 | 129,602 | 67,108,864B | 1 | 0 | true |

각 약 5.3초. 두 컨테이너와 업로드한 임시 스크립트/폴더를 정리했고, 해당 테스트 라벨의 잔여 컨테이너 0개를 확인했다. 기존 기본 운영 풀 7개 서비스는 모두 healthy였다.

종료 코드 0만으로 성공 판정하면 자식의 OOM을 놓칠 수 있다는 실제 재현이다. 이를 바탕으로 채점 분류에서 수집기가 제공한 자원 초과 증거를 먼저 확인하도록 수정하고 회귀 테스트를 추가했다. 출력 초과는 OLE, 컴파일 단계의 자원 초과는 별도 판정으로 분리한다. 컴파일 자원 오류는 대회 오답 패널티에서 제외하고 OLE는 실행 오답으로 포함한다.

## 이 결과로 완료 처리하지 않는 항목

실제 앱의 여섯 언어별 TLE/MLE/OLE, 최종 CPU 수집·감독 프로세스의 보안·컴파일 1회 후 케이스별 실행, 악성 프로세스 트리 정리, 자원 예약 스케줄링, 반복 성능 측정·확정 제한값은 아직 검증하지 않았다. 이 짧은 확인 값을 문제 제한 정책의 측정 증거로 사용하지 않는다. 디스크 96%·swap 전량 사용 상태라 큰 빌드/벤치마크는 시행하지 않았다.

계측 설계는 [Linux cgroup v2 문서](https://www.kernel.org/doc/html/v6.9/admin-guide/cgroup-v2.html)의 CPU/메모리 카운터 범위를 참고한다. 최신 커널의 memory.peak 재설정 기능을 현재 서버에서도 쓸 수 있다고 가정하지 않는다.
