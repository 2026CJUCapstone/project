# B++ 그래프 응답 속도 개선

## 현재 변경: 한 번의 컴파일로 그래프와 네이티브 검사

목표는 일반 예제에서 컴파일 버튼 클릭부터 실제 그래프 표시까지 3초 이내다. 대기 표시가 나타나는 시간이나 같은 코드를 재사용한 캐시 적중 시간을 목표로 삼지 않는다. 아래 19~22초 표는 **첫 번째 개선의 과거 측정**이며 현재 후보의 성능이 아니다.

- 통합 JSON의 IR을 제대로 읽도록 수정한 데 더해, 새 `compile-json` 실행 모드를 추가했다. 한 컴파일러 프로세스가 AST·IR·SSA·ASM JSON과 필터링하지 않은 네이티브 어셈블리를 함께 만든다. 별도 파일 디스크립터로 전달한 어셈블리를 NASM·링커로 검사한 뒤에만 JSON을 반환한다. 이전 이미지의 미지원 모드나 네이티브 오류를 성공으로 바꾸지 않는다.
- 가장 큰 병목은 GC의 음성 조회였다. 인덱스에 없는 임시 버퍼마다 모든 할당 기록을 재검색해 정리에 약 13초가 걸렸다. 인덱스가 완전한 경우에만 빠르게 없음을 반환하고, 인덱스 할당 실패 이후에는 기존 전체 검색을 유지한다. 이동·태그·해제·초기화 동작도 검증한다.
- **모든 함수의 의미 검사는 유지한다.** 검사를 마친 SSA 문맥을 첫 그래프에 재사용하고, 이후 그래프는 표시 대상 함수와 실제 호출 관계에 필요한 함수로 제한한다. 호출하지 않는 사용자 함수의 오류도 출력 전에 거부한다. 함수 포인터나 사용자 인라인 어셈블리처럼 연결을 확정할 수 없는 경우는 전체 분석으로 돌아간다.
- 단순 직접 호출 프로그램은 관계없는 표준 라이브러리 연산자 구현을 네이티브 출력에 포함하지 않는다. 기존 GC 도우미 수집은 유지하며, 사용자 연산자·소멸자·간접 호출은 보수적으로 처리한다. O0/O1 선택과 소스 범위를 변경하지 않는다.
- 어셈블리 캡처는 줄 경계 사이를 묶어서 복사한다. 부분 쓰기·빈 줄·마지막 개행이 없는 줄·캡처 재시작을 실제 실행으로 검사한다. 검사 중 발견한 빈 문자열의 `db ,0` 생성 오류도 `db 0`으로 수정했다.
- 서버는 Docker의 종료 알림을 한 번 기다린다. HTTP 요청과 코루틴에 시간 상한을 적용하고 종료 후 OOM 상태를 다시 읽는다. 컨테이너와 소스 디렉터리 정리를 하나의 영속 정리 기록으로 묶되, 컨테이너 삭제 응답이 불확실하면 소스를 지우거나 정리를 완료로 기록하지 않는다. 작업자는 기존과 같이 전체 작업의 자원 부재를 확인한 뒤에만 용량을 돌려준다.
- 프런트엔드는 처음 3초만 150ms 간격으로 결과를 조회하고 이후 750ms로 돌아간다. 초기 최대21회 GET이며 요청 재제출은 하지 않는다. 429의 Retry-After, 취소, 명시한 조회 간격과 대기 상한은 그대로 적용한다.
- 기본 조회 간격에는 요청·응답 처리 시간도 포함한다. 조회가 끝난 뒤 150ms를 다시 기다리지 않으며, 요청은 중첩하지 않는다. 사용자가 명시한 간격은 기존처럼 응답 이후의 대기 시간으로 적용한다.
- 접수 기록을 DB에 저장한 뒤 Redis에 작업 알림을 보낸다. 알림은 최대 한 바이트, 유효 기간 1초인 선택적 힌트다. 알림 누락·중복·Redis 장애 때도 250ms 주기의 기존 DB 조회가 남는다. 실제 실행 권한과 슬롯은 여전히 DB의 작업 임대가 결정한다. 컴파일 결과는 모델 검증·소유자 확인 이후 JSON 응답으로 바로 직렬화해 중복 순회를 줄인다.
- AST가 실제 트리 구조인지 확인한 뒤 선형 시간으로 배치한다. 순환·공유 자식처럼 트리가 아닌 입력과 SSA는 기존 일반 그래프 배치를 사용한다. 노드·연결·소스 범위는 삭제하지 않는다. 처음에는 현재 탭에 필요한 화면 데이터만 만들고, SSA/IR/ASM 탭이나 나란히 보기를 열면 해당 데이터를 준비한다. 숨겨진 미니맵의 크기 변경으로 불필요한 화면 갱신을 일으키지 않는다.

샌드박스 네트워크 차단·읽기 전용 파일 시스템·CPU/메모리/PID/출력 제한·작업별 단일 실행 슬롯은 해제하지 않았다. 일반 실행과 채점의 컴파일 모드는 그대로다.

### 재현 도구와 검증 구분

```text
python scripts/check_graph_latency.py --ssh-host USER@HOST --ssh-port 10022 --image sha256:IMAGE_ID --compiler-checkout LOCAL_BPP_GIT --output .deploy/graph-latency.jsonl
```

명시한 기존 이미지를 이용해 고정 소스의 모든 파일 해시를 검증한 뒤 격리 컨테이너에서 후보를 빌드한다. `--smoke`는 개발 확인용이며 전체 예제 검증으로 간주하지 않는다. `--export-candidate`는 테스트 디렉터리에 공개 바이너리와 소스만 보관하며 설치·배포하지 않는다.

- 기본 예제: 한글/이모지 출력, 조건문, 반복문, 중첩 반복문, 배열, 함수 호출/미사용 함수, 재귀, 포인터, 이진 탐색, 버블 정렬, 최대공약수, 동적 계획법.
- O0/LF와 O1/CRLF를 반복 실행한다. 실제 실행 파일의 출력과 기존/후보 그래프를 비교한다. 비교에서 허용하는 차이는 할당 순서에 따른 함수·명령 ID와 일관되게 바뀐 내부 어셈블리 라벨뿐이다. 명령·레지스터·분기·소스 오프셋·AST 연결·최적화 카운터는 그대로 비교한다.
- 함수 포인터, 인라인 어셈블리, GC 이동/인덱스 실패 후 복구, 캡처 줄 경계는 별도 정확성 사례다. 보수적인 분석 경로이므로 3초 성능 사례와 혼합하지 않는다.
- `verify_bpp_latency.py`의 짧은 설치 이미지 검사도 Docker 빌드에 연결했다. 네이티브 실행 6건과 어셈블/링크 오류 2건을 검사한다. 빌드 서버의 속도는 서비스 응답 시간으로 평가하지 않는다.
- `frontend/e2e/compiler-graph-latency.local.spec.ts`는 모의 응답 없이 실제 API를 사용하는 선택적 브라우저 검사다. 외부 JSON 예제 파일, 반복 수, O0/O1, 화면 너비를 지정할 수 있다. 클릭 시점을 기록하고 실제 결과 노드가 그려진 후 두 프레임까지 포함한다. O0는 AST와 SSA를 확인하며 O1은 서비스가 실제 제공하는 최적화 비교 화면을 측정한다.

브라우저 검사는 `RUN_COMPILER_LATENCY=1`, `COMPILER_LATENCY_CORPUS=절대경로`, `COMPILER_LATENCY_REPEAT=3`, `COMPILER_LATENCY_LEVELS=O0`, `COMPILER_LATENCY_VIEWPORTS=desktop:1440x1000`과 명시한 격리 API 주소로 실행한다. `COMPILER_LATENCY_COLLECT_ONLY=1`은 원인 분석용으로만 3초 단언을 생략하며 결과에도 이 구분이 남는다. 이 실행을 성능 합격으로 보고하면 안 된다.

### 현재 측정 상태

**현재 3초 목표는 완전히 충족하지 못했다.** 실제 기본 그래프 표시까지 대부분 3초 안에 도달했지만, 반복 측정의 초과 사례와 최적화 비교의 긴 응답이 남는다. 성공 사례만 골라 합격으로 처리하지 않는다.

| 실측 범위 | 3초 이내 | 클릭부터 표시까지 | 판정 |
| --- | ---: | ---: | --- |
| O0 기본 컴파일, 12종 × 3회, 데스크톱 | 32/36 | 2.548~3.176초 | 중간 결과; 가시성 측정 조건을 실행 중 강화해 최종 화면 판정으로 사용하지 않음 |
| O0 기본 컴파일, 12종 × 데스크톱·모바일, 최종 배율 수정 후 | 22/24 | 2.557~3.043초 | 24회 모두 실제 AST·SSA 표시; 중첩 반복문 3.043초, 포인터 3.037초로 성능 단언 실패 |
| O1 최적화 비교, 출력·중첩 반복문·포인터 × 세 화면 크기 | 5/9 | 2.681~3.913초 | 9회 모두 기능 성공, 4회 성능 단언 실패; 일부 마지막 실행과 로컬 회귀 작업의 중첩 가능성도 남김 |

기본 컴파일 최종 검사는 데스크톱 1440×1000, 모바일 390×844에서 실시했다. 최적화 비교에는 태블릿 1024×900도 포함했다. 그래프가 화면·캔버스 안에 실제로 나타났는지 검사하며, 로딩 표시나 화면 밖 DOM 노드로 통과시키지 않는다. 이전 모바일 검사에서 큰 AST가 최소 배율 0.2에 막혀 잘렸고, 최소 배율을 0.05로 낮춰 24회 모두 표시를 확인했다. 큰 그래프는 전체 개요로 보이며 확대해서 읽을 수 있다.

원시 보고서는 `.deploy/latency-split-browser-desktop.json`, `.deploy/latency-viewport-fit.json`, `.deploy/latency-o1-viewports.json`에 있다. 실제 컴파일러·어셈블·링크만의 최종 O0/O1 검사는 일반 사례 약 1.6~2.1초, 포인터 약 1.9~2.4초였다. 큐·컨테이너 준비·전송·화면 표시 시간은 이 수치에 포함되지 않는다. 함수 포인터와 사용자 인라인 어셈블리는 보수적 전체 분석으로 약 5.5~7.6초가 걸리는 별도 예외다.

중간 실패도 보관한다. 대기/화면 개선 전 12종 × 3회는 18회만 3초를 통과했고 최대 3.477초였다. 트리 배치·작업 알림·직접 JSON 응답 적용 후, 조회 간격 보정 전에는 30/36회 통과, 나머지 6회는 3.027~3.108초였다. 같은 소스를 재사용하더라도 매번 새 실행 접수·새 샌드박스·새 컴파일러 프로세스로 실행했다. 결과 캐시는 사용하지 않지만 서버의 파일 시스템 캐시까지 비운 콜드 부팅 시험은 아니다.

테스트 API는 운영과 분리된 PostgreSQL·Redis·작업 큐를 사용한다. 최종 검사는 운영 Compose와 같이 API 0.75 CPU와 작업자 1 CPU를 분리하고 각각 메모리 512MiB로 제한했다. 이전 진단은 API와 작업자가 1 CPU를 공유했으므로 별도 조건이다. 기존 이미지에 해시를 확인한 후보 소스·컴파일러를 읽기 전용으로 연결했다. 브라우저는 로컬 프로덕션 프런트 빌드와 SSH 터널로 이 API에 접속한다. CPU 1개/메모리 256MiB인 실행 샌드박스의 제한은 유지했다. 이 결과를 새 설치 이미지·운영 HTTPS 경로·동시 부하 검증으로 대신하지 않는다.

### 정확성·회귀 검증

- 실제 고정 컴파일러와 후보의 8종 × O0/O1 × 3회 그래프·소스 의미 비교와 네이티브 실행 통과. 추가 알고리즘 4종 × O0/O1 × 3회 실제 출력도 통과.
- 함수 포인터·인라인 어셈블리·GC 인덱스/이동·ASM 캡처 4종 × O0/O1 통과. 호출하지 않는 함수의 오류를 포함해 의미 오류 4건 거부.
- 설치 형식의 실행기 검사: 실제 네이티브 실행 6건, NASM·링커 실패 시 성공 JSON 미출력 2건 통과. 전체 설치 이미지 빌드와는 구분한다.
- 실제 격리 API에서 한글·이모지 LF/O0, CRLF/O1 두 요청의 AST·SSA·IR·ASM 소스 범위, 변수 정의/사용, 최적화 카운터 검사 통과.
- 실제 Chrome의 모의 컴파일 응답 기반 상호작용 검사 2건 통과: 드래그, 검색, 선택 집중, 접기, 단계 연결, 나란히 보기, 변수 흐름, 모바일·태블릿·데스크톱. 위 실제 API 소스 검사까지 Playwright 3건 통과.
- 프런트엔드 70개 파일 / 398개 테스트, 타입 검사, 프로덕션 빌드 통과. 큐·접수 API·작업자 관련 38개 테스트와 실제 격리 Redis 알림/TTL/크기 검사 1개 통과. 최종 전체 백엔드 **3,344 통과, 466 건너뜀, 하위 테스트 19 통과**(464.32초). 외부 환경 때문에 건너뛴 항목은 통과로 간주하지 않는다. Python 구문 검사와 `git diff --check`도 통과했다.

남은 성능 목표는 반복 실행에서도 3초를 넘지 않을 충분한 여유를 확보하는 것이다. 특히 전체 의미 분석 비용, 새 샌드박스 준비, 최적화 처리와 완료 알림 지연을 더 줄여야 한다. 제한을 늘리거나 결과 캐시를 적중시킨 측정으로 대신하지 않는다.

컴파일러 자체를 O1로 다시 빌드하는 추가 실험도 했다. 출력·중첩 반복문·포인터의 O0/O1 6건은 네이티브 결과와 그래프가 일치했으나, 5건에서 기존 후보와 같거나 더 느렸다(출력 O0 1.62→1.75초, 포인터 O0 1.85→1.95초). 짧은 진단 결과이므로 일반화하지 않으며 해당 빌드 방식은 채택하지 않았다. 실험용 컴파일러를 설치하거나 기존 후보를 교체하지 않았다.

검사가 끝난 전용 API·작업자·PostgreSQL·Redis 컨테이너와 격리 네트워크는 정확한 ID를 확인해 제거했다. 임시 테스트 DB는 메모리 전용으로 폐기되었고 운영 DB·이미지·서비스는 변경하지 않았다. 측정 로그와 후보 소스/바이너리는 증거로 남겼다.

## 이전 단계 기록: 중복 IR 실행 제거

## 범위와 원인

IDE의 전체 컴파일 요청은 기존에 네이티브 컴파일 검사 → 통합 JSON → 별도 IR JSON 순서로 실행했다. 각각 별도 샌드박스를 사용한다. 고정된 B++ `9859a2dc783c9346be2ab9447e1569218bcc5093`은 통합 결과에도 IR을 출력하지만, 실제 구조는 `views.ir.ssa`이며 내부 `stage`가 `ir`이다. 서버 파서가 이 중첩을 처리하지 못해 이미 생성한 IR을 다시 생성했다.

## 변경

- IR 파서가 통합 결과의 SSA 형태 컨테이너를 해제하되 `stage=ir|machine-ir`일 때만 받는다. 실제 SSA 단계를 IR로 바꾸어 표시하지 않는다.
- 정상적으로 파싱된 빈 뷰는 완료로 처리한다. 소스 필터링 결과가 비었다는 이유로 추가 컨테이너를 만들지 않는다.
- 최신 통합 결과는 네이티브 검사 → 통합 JSON 두 번으로 완료한다. 네이티브 어셈블·링크 검사는 제거하지 않는다. 실제 실행과 문제 채점 경로는 변경하지 않는다.
- 구형 또는 불완전한 JSON에는 기존 별도 IR JSON/텍스트 호환 경로가 남는다.
- B++ 출력 패치에서는 내부 IR/SSA 출력 함수가 외부 통합 출력의 버퍼링을 해제하지 않게 한다. 별도 IR 출력은 기존처럼 버퍼를 비우고 종료한다. 소스 매핑과 최적화 패스는 바꾸지 않는다.

## 재현과 검증

단위·서비스 회귀는 `backend/tests/test_compiler_unified_ir.py`에 실제 중첩 구조, 한글·CRLF 바이트 범위, 잘못된 단계 거부, 전체/빈 뷰의 실행 횟수, 구형 JSON 호환, 네이티브 오류·출력 제한 중단을 포함한다.

실제 런타임 검증 도구는 `scripts/check_compiler_performance.py`다. 명시한 기존 이미지와 고정 B++ 소스를 이용한다. 내려받은 소스는 로컬 Git 내용의 SHA-256으로 파일별 검증하며, 운영 볼륨·DB·큐를 연결하지 않는다. 컨테이너는 네트워크 차단, 읽기 전용 루트, 비특권 사용자, CPU 1개, 메모리/스왑 1 GiB 동일 상한, PID 64, 임시 실행 공간 256 MiB 제한이다. 종료·실패 시 해당 테스트 컨테이너만 제거한다.

예시 실행(이미지 ID와 SSH 대상은 검증할 환경에 맞춰 명시):

```text
python scripts/check_compiler_performance.py --ssh-host USER@HOST --ssh-port 10022 --image sha256:IMAGE_ID --compiler-checkout LOCAL_BPP_GIT --output .deploy/compiler-performance.jsonl
```

한글 포함 조건문·함수 호출 예제로 LF/CRLF × O0/O1을 각각 3회 측정하고, 기존/후보 통합 JSON의 전체 내용 동등성과 통합 IR/별도 IR 동등성을 검사한다. 실제 소스 매핑 파싱, 잘못된 코드 4건 거부, 배열·포인터 네이티브 실행 O0/O1도 확인한다.

측정치는 프로세스 실행 구간이다. 컨테이너 시작·큐 대기·네트워크·브라우저 렌더링을 포함한 운영 응답시간이나 동시 사용자 부하 시험으로 해석하지 않는다. 네이티브 검사를 유지한 상태의 전후 구간 합을 비교한다.

네이티브 구간은 구현이 변경되지 않아 각 반복에서 측정한 같은 값을 전후 합산에 사용했다. 후보/기존 JSON 실행 순서를 교대했다. 통합 JSON 출력 자체의 시간은 비슷했고, 버퍼링 수정만으로 유의미한 속도 향상을 주장하지 않는다. 주된 효과는 불필요했던 별도 IR 실행 제거다. 여전히 표준 라이브러리를 포함한 분석 비용이 남아 있으므로 즉각적인 응답 수준에 도달한 것은 아니다.

- 네 조합 × 3회: 기존/후보 통합 JSON 전체 일치, 통합 IR/별도 IR 전체 일치, 출력 용량 상한 통과.

- 잘못된 코드 4건: JSON 출력 전 거부. 호출하지 않는 함수 내부 오류도 포함.
- 배열·포인터 네이티브 코드 O0/O1 총 4건: 실제 출력 확인.

- 구문 검사와 `git diff --check` 통과. 프런트엔드 변경 없음. 이번 변경의 브라우저 실측·운영 배포·동시 부하 시험은 수행하지 않음.

## 배포 조건 (현재 후보에 적용)

**현재 백엔드의 `compile-json`은 새 컴파일러와 실행기를 요구하므로 백엔드만 따로 배포하면 안 된다.** 컴파일러 패치·실행기·검사 파일은 빌드 서명에 포함된다. 배포 승인을 받은 뒤에도 정확한 여섯 runtime 파일 집합만 승인하는 별도 프로필을 사용한다. 전체 이미지 빌드, 보안 검사, 설치 이미지/다중 언어/탐색 기능 회귀, 정확한 런타임 digest·불변 image ID·이전/후속 commit 승인을 모두 통과해야 앱과 런타임을 함께 전환할 수 있다. 이후 운영 브라우저의 실제 응답 시간과 소스 연결을 재검증한다. 동시 사용자 부하나 임의 크기 소스에서 3초를 보장한 결과가 아니다.
