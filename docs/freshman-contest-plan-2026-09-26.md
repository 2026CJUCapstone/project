### 2.1 비공개와 날짜 수정

- 비공개 초안은 구성과 일정을 수정할 수 있다. 공개한 예정 대회도 시작 전에는 수정 가능하다.
- 시작한 공개 대회는 일정·문제·배점을 변경하지 않는다. 비공개 초안의 임시 날짜가 지났다면 공개 전에 미래 날짜로 수정한다.
- 날짜만 변경했을 때 테스트·문제 스냅샷·언어별 제한 버전이 바뀌지 않는지 검증한다.
- 문제는 대회 생성 API의 신규 비공개 문제로 작성한다. 일반 공개 문제로 먼저 등록한 뒤 숨기는 방법은 사용하지 않는다.
- 문제 목록·검색·직접 URL·학습/추천·제출 내역·큐·커뮤니티·캐시에서 비공개 내용이 새지 않아야 한다.
- 현재 정책은 공개 대회의 종료 시각에 신규 문제를 일반 문제로 노출한다. 최종 채점이 남아 있어도 공개 조건이 바뀐다.
- **종료 후에도 계속 비공개로 둘지** 등록 전에 결정한다. 계속 비공개라면 별도의 공개 정책이 필요하다.
- 검증하려고 운영 날짜를 앞당기거나 운영 대회를 잠시 공개하지 않는다.

- ICPC U의 [콘텐츠 거버넌스](https://u.icpc.global/governance/)도 외부 문제는 기록된 라이선스가 없는 한 원 소유자에게 권리가 남는다고 안내한다. 다른 지역 대회의 별도 공개 라이선스를 Banks에 일반화하지 않는다.
- 원문 URL, 대회/저자, 원문 티어 확인일, 이용 조건과 변경 내역을 출제 기록에 남긴다.

- 이용 조건을 확인하지 못한 후보는 보류한다. 일반 알고리즘 주제만 참고한 독립 창작으로 대체한다면 사용자에게 알린다.
- 블로그의 번역·해설·코드를 복사하거나 다른 저지의 숨김 테스트를 무단 수집하지 않는다.
- 이야기와 표현은 새로 쓰되 수학적 의미, 입력·출력, 예외 조건은 보존한다. 검색이나 출처 추적을 피하려는 각색으로 만들지 않는다.
- 새 예제를 직접 만들고 독립 기준 풀이로 결과를 검증한다.
- 등록용 지문·예제·정답 코드·생성기·검증기·느린 풀이·대표 오답을 하나의 출제 패키지로 검수한다.
- 완성 지문은 별도 문서에서 사용자 승인을 받은 뒤 업로드한다.

## 4. J — Banks 번역·각색 계획

2026-09-26 후속: [문제 지문 문서의 J절](freshman-contest-statements-a-i-2026-09-26.md#j-원형-연구실의-자원-조정)에 참가자용 각색 초안을 작성했다. 새 예제 4개의 최소 횟수와 작은 변형 42개·초기 완료 1개를 로컬 탐색으로 검증했다. 전체 정답 알고리즘·이용 조건·실제 채점 검증 완료는 아니다.

원문은 **SEERC2014 Problem A, Banks**다. 다음은 기획용 의미 요약이지 등록용 완성 번역문은 아니다. [원 출제처 PDF](https://seerc.icpc.global/2014/prob/probleme/A.pdf)

원형으로 연결된 지점마다 정수 자원이 있고 전체 합은 양수다. 음수 지점의 값을 양수로 뒤집을 때 양옆 지점에서 그 절댓값을 각각 차감한다. 모든 값이0 이상이 되기 위한 최소 연산 수를 구한다. 원문 범위는1≤n<10000, -32000<k_i<32000이다.

### 4.1 필수 검수

- 은행 대신 연구실의 자원 조정으로 배경을 바꾸되 연산과 전체 합 조건을 유지한다.
- n=1·n=2처럼 이웃이 자기 자신 또는 같은 지점과 겹치는 경우의 연산 의미를 원문/공식 자료와 대조한다. 같은 이웃에 대한 차감을 임의로 한 번만 적용하지 않는다.
- 0은 목표 조건을 만족하고 연산 대상은 음수라는 점을 명확히 한다.
- 중간 값·정답 연산 수의 상한을 증명한 후 정수형을 결정한다. JavaScript Number로 충분한지, BigInt가 필요한지 별도 확인한다.
- 최적성 증명을 갖춘 기준 풀이와 독립 구현을 준비한다. 작은 입력은 완전 탐색 등으로 대조하되 그것만으로 큰 입력의 정당성을 주장하지 않는다.
- 원형 회전·양의 배수 변환 등 검증한 수학적 성질을 이용한 추가 검사를 구성한다.
- 이용 조건·완성 번역·정답 증명·테스트가 준비되지 않으면 J는 출제 보류한다. 샘플만 있는 미검증 문제를 공개하지 않는다.

### 4.2 GPT 사용 확인에 관한 운영 원칙

J를 맞혔다고 GPT 사용이 확정되지 않으며, 틀렸다고 미사용이 증명되지도 않는다. 원문을 이미 아는 사람이나 실력이 높은 참가자도 있을 수 있다.

- AI·검색·외부 코드·타인 도움의 허용 범위를 참가 전에 공개한다.
- 일부 풀이에 대해 접근 방법, 복잡도, 코드 설명, 작은 변형 문제를 확인할 수 있음을 사전 고지한다.
- 정답 여부·풀이 속도·코드 유사도·설명 부족 중 하나만으로 자동 제재하지 않는다.
- 제출 이력과 설명은 보조 자료로 사용하고, 설명 기회와 이의 제기 절차를 거쳐 사람이 판단한다.
- 참가자 소스를 외부 AI 탐지 서비스로 임의 전송하지 않는다. 접근자와 보관 기간을 제한한다.
- J를 'GPT 탐지기'로 소개하거나 숨겨진 실격 조건으로 사용하지 않는다.

## 6. 언어별 자원 제한 정책

2026-09-26 공식 자료 조사 반영: [AtCoder·Codeforces·DOMjudge 비교와 적용안](judge-language-limits-references-2026-09-26.md). 종전의 추가 시간과 256/512MiB 표는 확정 기본값에서 제외한다. 아래 값은 측정 출발점이며 실제 운영 적용은 아직 하지 않았다.

### 6.1 적용 원칙

- 기본 시간 × 언어별 계수를 출발점으로 삼되, 실제 측정으로 확정한 문제별·언어별 제한을 우선한다.
- 제한은 **테스트 케이스별 실행**에 적용한다. 큐 대기·이미지 준비·컴파일·출력 검사기 시간은 제외한다.
- 실행 시 런타임 시작·JIT·GC 비용은 포함하며 언어별 여유에 반영한다.
- 공개 시 최종6개 언어 제한표와 정책 버전을 대회 문제에 복사한다. 접수 시 작업 payload에도 복사한다.
- 클라이언트가 제한을 지정하지 않는다. 서버가 문제 스냅샷에서 확정한다.
- 재시도·재시작·전역 설정 변경에도 이미 접수된 작업은 동일 제한을 사용한다.
- 이미지 digest, 컴파일 옵션, 테스트 묶음 hash를 기록한다. 시작 후 정책을 조용히 변경하지 않는다.
- 서비스 최대 허용 예산을 넘는 설정은 저장/공개 단계에서 거절한다. 낮은 값으로 조용히 잘라 TLE를 만들지 않는다.

문제별 시간 × 언어 계수와 CPU/wall 분리는 [DOMjudge 9.0](https://www.domjudge.org/docs/manual/9.0/judging.html)을 참고한다. 시간 보정의 수치 사례는 [Codeforces의 특정 대회](https://codeforces.com/group/hNnRWqFua0/contest/473412/extraTimeFactors)에서 확인했으며 모든 대회 공통 정책으로 일반화하지 않는다. AtCoder에서 보편적인 언어 배수는 확인하지 못했으므로 AtCoder 표준 배수라고 주장하지 않는다.

### 6.2 공식 사례를 참고한 측정 출발점

기본 CPU 시간 B초에 대해 초벌 후보는 max(B × 언어 배수 + 근거 있는 추가 시간, 실측 기동 여유)다. 추가 시간은 기본0으로 두며, 기존 +0.2/+0.3/+0.5초는 근거가 확정되지 않아 제거한다. 정답 풀이 실측에 기동·JIT가 포함됐다면 이를 다시 더하지 않는다.

| 언어 | 실험용 배수 | 근거 | 메모리 |
| --- | ---: | --- | --- |
| C | 1.0 | 자체 비교 기준 | 문제·런타임별 실측 후 확정 |
| C++ | 1.0 | 자체 비교 기준 | 문제·런타임별 실측 후 확정 |
| B++ | 1.0 | 임시 출발점, C++ 동등 성능 보장 아님 | 문제·런타임별 실측 후 확정 |
| Python | 5.0 | 해당 Codeforces의 Python 3 사례 | 시간 배수와 독립적으로 확정 |
| Java | 1.5 | 해당 Codeforces의 Java 8/21 사례 | JVM 포함 전체 피크와 여유 측정 |
| JavaScript | 3.0 | 해당 Codeforces의 Node.js 사례 | V8·Buffer 등 포함 전체 피크 측정 |

이 표는 우리 사이트의 확정 제한이 아니다. 문제별·런타임 버전별 정답/느린 풀이 비교 후 CPU ms·wall ms·메모리 bytes의 **절대값**을 확정해 저장한다. 미측정 신규 문제는 공개하지 않는다.

비교 후보로 BOJ형 정책도 표현한다. [공식 언어 정보의 2026-04-18 보존본](https://web.archive.org/web/20260418193203id_/https://help.acmicpc.net/language/info)은 Python3 시간3T+2초/메모리2M+32MB, Java11 시간2T+1초/메모리2M+16MB, Node.js 시간3T+2초/메모리2M을 게시한다. 이는 현재 설정 보장이 아니고 문제별 예외가 있다. Codeforces형 배수와 BOJ형 보정을 중첩하지 않는다. 시간·메모리의 계수/추가량은 독립 필드로 두되 실제 최종 제한은 측정으로 확정한다. MB와 MiB의 단위도 명시적으로 변환한다.

메모리는 정상 풀이 전체 프로세스 트리의 피크와 기록된 안전 여유를 기준으로 정하며, 가상 주소 예약량이나 시간 배수로 산정하지 않는다. 전체 피크에는 런타임이 이미 포함되므로 JVM 기본 사용량을 다시 더하지 않는다. AtCoder의 특정 문제에 표시된 1024MiB도 우리 기본값으로 복사하지 않는다.

wall = max(2 × CPU + 1초, CPU + 2초)는 기존 자체 실험 후보일 뿐 공식 표준이 아니다. 정상 동시성·런타임 대기를 측정한 뒤 별도 절대 한도로 확정한다. DOMjudge식 overshoot를 도입할 경우 판정 한도와 강제 종료 한도를 구분하고, 초과분을 AC 여유로 처리하지 않는다.

- B++의 I/O·배열·큐 성능을 실제 버전으로 측정한다. 네이티브라는 이유만으로 C++와 같은 성능으로 확정하지 않는다.
- Python은 실제 제공 인터프리터로 측정한다. 검증하지 않은 PyPy 성능을 사용하지 않는다.
- JVM heap/Node old-space는 전체 cgroup 한도보다 작게 설정하고 네이티브 메모리·스레드 여유를 실측한다.
- 가상 주소 예약량을 실제 사용 메모리처럼 취급해 JVM을 즉시 MLE 처리하지 않는다.
- 언어 런타임·자식 프로세스·참가자 tmpfs 사용량은 메모리 예산에 포함한다. 외부 채점기·입력 준비 비용은 분리한다.
- 6개 언어 모두 기준 풀이가 통과해야 한다. 특정 문제의 지원 언어를 제한해야 한다면 설정·표시·참가 규칙을 먼저 승인받는다.

### 6.3 실행 구조와 계측

1. 컴파일은 별도 예산으로 한 번 수행하고 작업 전용 산출물을 만든다.
2. 각 테스트는 새 격리 실행 환경에서 동일한 읽기 전용 산출물을 실행한다. 제출 간 산출물을 공유하지 않는다.
3. 신뢰 가능한 외부 감독자가 실행 프로세스 트리의 CPU·wall·메모리 피크·OOM 이벤트를 측정한다.
4. CPU 코어 할당량은 CPU 시간 예산을 대신하지 않는다. 자식 프로세스와 스레드도 합산한다.
5. stdout/stderr 합산 출력 상한을 둔다. 초기1MiB 후보이며 초과 시 수집과 실행을 중단한다.
6. 전체 프로세스 트리·컨테이너·임시 파일을 정리하고 작업 슬롯 반환을 확인한다.
7. 네트워크 차단·읽기 전용·권한 축소·PID/파일/임시 공간 제한은 그대로 유지한다.

컴파일 CPU30초/wall60초/메모리1GiB는 검증 출발점이다. 실제 호스트 용량에 맞는 별도 컴파일 동시성 한도가 필요하며, 운영값으로 바로 적용하지 않는다.

전체 작업 deadline = 컴파일 한도 + 케이스별 wall 한도의 합 + 제한된 준비/정리 여유.

예를 들어 확정된 케이스별 wall 한도가10초라고 가정하면40케이스의 실행 예산만400초다. 이는 산술 예시이지 Python의 확정 한도가 아니다. 기존 공통120초를 그대로 적용하면 정상 채점이 중단될 수 있다. 최대 작업 한도, 케이스 수, 케이스 크기, 조기 실패 종료를 함께 설계하고 허용 예산을 넘는 출제 패키지는 공개 단계에서 거절한다.

언어별 메모리 한도를 달리하면 워커 슬롯 수뿐 아니라 컴파일/실행 작업의 예약 메모리 합도 제한한다. 운영 여유를 뺀 호스트 예산을 넘기지 않고, 측정한 CPU 등급의 워커에 배치한다.

### 6.4 제한 확정 방법

- 대회와 같은 실행 이미지/CPU 환경에서 문제별6개 언어 기준 풀이를 최소10회 실행한다.
- 최초 기동·반복 실행·정상 동시성 부하를 구분하고 CPU/wall/메모리 최대·편차를 기록한다.
- 정답 풀이가 제한 근처에서 흔들리지 않도록 여유를 둔다.
- [DOMjudge의 출제자 풀이 검증 안내](https://www.domjudge.org/docs/manual/9.0/config-basic.html#testing-jury-solutions)는 가장 느린 정답의 약2배를 경험칙으로 제시한다. 이를 검토 출발점으로 사용하되 의무 배수나 모든 문제에서의 보장으로 취급하지 않는다.
- 느린 풀이도 동일 입력에서 측정한다. 정답과 느린 풀이의 시간이 겹치면 배수를 억지로 줄이지 말고 출제/입력을 수정한다.
- 제한값 변경 후 모든 언어의 정답·오답·자원 초과 회귀를 다시 실행한다.
- 측정표에 호스트·이미지 digest·테스트 hash·한도·실측값·판정·반복 횟수를 남긴다.
- 문제 화면과 IDE는 선택 언어의 실제 CPU/wall/메모리 한도와 전체 언어 표를 보여준다. 화면/API/큐/실행기 값의 일치, 미확정 공개 거절, 정책 변경 중 재시도 고정을 검증한다.

## 7. 판정 정의

| 판정 | 인정 근거 | 주의점 |
| --- | --- | --- |
| AC | 정상 종료 및 모든 출력 일치 | 점수 한 번 지급 |
| WA | 정상 종료 및 출력 불일치 | 공백 정책 사전 고정 |
| CE | 컴파일러의 실제 소스 진단 실패 | 실행 RE와 분리 |
| TLE | 감독자의 CPU 또는 wall 한도 초과 | 큐 대기/이미지 준비는 제외 |
| MLE | 실행 cgroup의 한도 초과/OOM 증거 | exit137/오류 문자열만으로 단정 금지 |
| RE | 비정상 종료·신호·미처리 예외 | 직접 exit124/137도 근거 없이 자원 초과로 바꾸지 않음 |
| OLE | 외부 출력 수집기의 상한 초과 증거 | 현재 RE 합침 개선 필요 |
| 시스템 오류 | 워커·도커·이미지·감독자·계측 실패 | 참가자 오답 페널티 제외 |

- Python MemoryError, Java OutOfMemoryError, C++ bad_alloc 등도 실제 제한 근거를 확보해야 MLE로 분류한다. 동일한 문자열을 출력하는 프로그램은 자원 초과 증거가 아니다.
- 런타임 한도 증거가 없으면 RE로 남기고 관리자 진단에 원인을 기록한다. 가짜 문자열 탐지로 MLE를 늘리지 않는다.
- 컴파일 자원 초과는 소스 문법 CE와 구분해 기록하고 오답 페널티에서 제외한다.
- 여러 자원 제한이 동시에 발생하면 최초로 입증된 사건을 기준으로 하며 원인/시각을 보존한다. 호스트 OOM은 학생의 MLE로 돌리지 않는다.
- 계측 누락을0초/0MiB나 성공으로 해석하지 않는다.
- 숨김 입력·기대 출력·실제 출력은 참가자에게 보내지 않는다.
- 기존 WA/RE/TLE/MLE 페널티를 유지하고 OLE 추가 시 동일한 오답 정책을 명시한다. CE/컴파일 자원 오류/시스템 오류는 제외한다.

| V12 | 격리 PID 한도 초과 | 명시된 실패 판정, 호스트 장애 없음 |

CPU 검증을 sleep만으로 대신하지 않는다. 메모리는 주소 예약만 하지 않고 실제 페이지를 사용한다. 경계 테스트는80%/120% 목표 교정 프로그램에서 시작해 실제 계측을 보고 조정한다. 출력 경계는 정확히 한도/한도+1과 UTF-8 바이트를 확인한다.

비공개 검수는 동일 채점 모듈을 쓰는 격리 환경의 패키지 검증 도구로 수행한다. 현재 참가자 제출 API를 우회하지 않는다. 관리자 웹 검수 버튼이 필요하면 관리자 전용 API·무점수·숨김 출력 보호·실행 제한을 별도 구현한다.

### 8.4 환경과 안전 조건

- 가짜 실행기/SQLite 검증은 UI·권한·점수 로직에만 해당한다.
- 실제 자원 초과는 Linux·Docker/cgroup·실제 언어 런타임으로 검증한다.
- 운영 서버를 쓰더라도 별도 승인 후 스테이징 DB/네트워크/큐/워커/파일 공간을 격리한다. 운영 DB·Redis·점수판을 공유하지 않는다.
- 테스트 환경 전체 메모리·디스크·동시성 상한과 중단 기준을 먼저 설정한다. 운영 지연이나 호스트 OOM 위험이 나타나면 중단한다.
- 과거 배포 기록에는 샌드박스 보안 미해결98건과 해당 배포의 한정 예외가 있다. 이는9월26일 재스캔 결과가 아니다. 이번 대회 전에 현재 이미지 보안 상태를 다시 검토하며 이전 예외를 자동 재사용하지 않는다.
- 화면이 열리거나 Hello World가 성공했다는 이유로 MLE/TLE·대회 전체·보안 검증 완료라고 보고하지 않는다.

## 9. 구현 작업 목록

1. ruby 난이도를 API/UI/정렬/필터/통계에 일관되게 추가한다. 기존 등급 레이팅 값을 밀거나 이전 점수를 임의 재계산하지 않는다.
2. 문제별 CPU ms·메모리 MiB·언어별 확정값·출력/PID 제한·정책 버전·지원 언어 모델을 추가한다.
3. 대회 스냅샷과 durable 작업 payload에 해당 정책을 고정한다.
4. 컴파일1회/케이스별 실행으로 분리하고 신뢰 가능한 CPU·wall·메모리 계측을 연결한다.
5. OLE와 컴파일 자원 오류를 구분하고 참가자 설명/관리자 진단을 분리한다.
6. 문제 패키지 검증 도구와 측정 보고서를 만든다.
7. 대회 편집 화면에 언어별 제한표·검수 상태·출처 정보를 제공한다.
8. 기존 문제는 명시적인 legacy 정책으로 보존한다. 진행 중 대회의 제한을 자동 변경하지 않는다.
9. 오류 수정 후 재채점은 관리자 작업·정책 버전·변경 이력을 남긴다. 종료 순위를 조용히 덮어쓰지 않는다.
