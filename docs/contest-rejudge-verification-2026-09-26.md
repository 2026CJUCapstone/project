# 대회 재채점과 점수 정정 — 구현·검증 기록

## 현재 범위

운영 반영 전 로컬 구현이다. 운영 등록·데이터 수정·배포·Git push는 하지 않았다. v17 후보 처리, v18 해결 근거/감사 테이블, v19 점수 미리보기, v20 정정본 검수, v21 대규모 캠페인, v24 과거 해결 출처 해소 절차를 추가했다. 원래 제출의 접수 시각과 실행 요청은 바꾸지 않는다.

1. 관리자는 종료·최종 채점 완료 대회에서 수정한 테스트와 새 제한 정책을 제출한다. 본문과 배점은 유지한다. 같은 정책 ID의 증가한 버전, 테스트 해시, 등록 런타임/측정 근거와 저장 참조 무결성을 검사한다.
2. 코드·언어·접수 시각·원래 결과 지문을 별도 보관하고 수정 정책을 제출별로 고정한다. 원래 제출·점수는 유지한다.
3. 유지보수 작업은 기존 durable queue에 최대 4건씩 배정하며 일반 작업과 전체 용량 및 유지보수 쿼터를 공유한다. 미배정 항목은 재시작 후 복구한다.
4. 작업 소유권을 검증한 계측 결과만 후보에 기록한다. 인프라 오류/취소가 있으면 반영 준비 상태가 되지 않는다. 후보 채점만으로 점수는 바뀌지 않는다.
5. 별도 apply 요청은 요청 해시와 점수판 버전, 원래 문제 스냅샷, 제출 집합/참가 기록과 제출별 지문을 다시 검사한다. v19에서는 점수 미리보기 해시도 필수다. 동일 요청은 한 번만 반영한다.
6. 수정 판정·정책·일반 해결 점수·점수판 버전·감사 기록을 한 트랜잭션으로 반영한다. 오류면 전부 취소한다. 공개 정정 설명은 비공개 작업 사유와 구분한다.

v21부터 한 캠페인을 제출 1,000개/소스 64 MiB 이하의 결정적 shard로 나눈다. 캠페인 자체의 안전 상한은 제출 10,000개/소스 512 MiB이며, 이 값은 운영 승인 전 코드 상한이지 신입생 대회의 승인된 규모가 아니다. 큐 요청은 2 MB보다 작게 여유를 두고 검증한다. 반영 전 SQL에서 계측 JSON 크기를 제한한다. 감사 점수판은 참가자×문제 20,000칸 이하, 전후 감사 자료는 16 MiB 이하로 제한한다. shard별 부분 반영은 제공하지 않고 캠페인 전체를 한 번에 반영한다.

## 해결 근거와 과거 기록

solve_evidence에는 코드 없이 사용자·문제·근거 종류/ID·시각·배점·유효 여부를 보관한다. 일반 기록 보관 개수 제한으로 삭제하지 않는다. 중복 정답도 근거로 남기지만 점수는 한 번만 지급한다.

- 일반 정답, 종료한 대회 정답, 관리자 수동 지급을 구분한다.
- 특정 대회 제출이 오답이 되면 그 근거만 무효화한다. 다른 정답 근거가 있으면 기존 지급액을 유지한다.
- 유효한 근거가 전부 사라지면 기존 지급액을 차감한다. 새 정답에는 대회 스냅샷의 일반 문제 배점을 사용한다.
- 출처 없는 기존 점수는 legacy로 보존한다. 그 기록만 남았는데 차감이 필요하면 409로 전체 반영을 거절한다. 관리자는 v24의 별도 절차에서 `출처 미확인 상태로 유지`하거나 이미 존재하는 accepted 일반/대회 영수증에 연결할 수 있다. 원래 legacy 근거를 다시 쓰거나 출처를 만들어 넣지 않는다.
- 해결 상태 변경 시 커밋 후 레이팅 캐시를 무효화한다. 운영 데이터 소급 보정은 실행하지 않았다.

## API와 감사

/api/v1/contests/{contestId}/rejudges 아래 관리자 전용 API는 no-store다.

| 동작 | 경로/의미 |
|---|---|
| GET context | contestProblemId의 비공개 스냅샷/해시 |
| POST 목록 경로 | requestId로 멱등 후보 생성 |
| GET 목록 경로 | offset/limit 묶음 목록 |
| GET {batchId} | 제출별 전후 판정 페이지/반영 메타데이터 |
| POST {batchId}/discard | 실행 완료 후보 폐기, 운영자/시각 보존 |
| GET {batchId}/preview | 쓰기 없이 전후 순위·점수·일반 점수 증감·차단 사유와 previewHash 조회 |
| GET {batchId}/legacy-resolutions | legacy 차단 후보와 append-only 해소 이력 조회 |
| POST {batchId}/legacy-resolutions | 명시적 유지 또는 기존 accepted 영수증 연결 기록 |
| POST {batchId}/apply | expectedRequestHash, expectedScoreboardRevision, expectedPreviewHash, publicNote 명시 반영 |
| GET {batchId}/audit | 전후 순위·점수·일반 점수 증감 페이지 |

감사 테이블은 원래 스냅샷/계측/판정과 전후 점수판, 증감, 반영 관리자/시각을 보존한다. 공개 대회와 점수판에는 최근 20개 정정의 공개 설명·시각·버전 및 전체 개수만 제공한다. 다른 사람의 코드·숨김 테스트·비공개 작업 사유·원본 보고서는 공개하지 않는다. 컴파일 기록은 원래 실행 이력으로 유지하며 정정 이력과 구분한다.

관리자 이력 UI에는 목록/항목 페이지 이동, 반영 상태, 권한/조회 오류 시 민감 기록 정리, 작은 화면의 키보드 접근 가능한 가로 스크롤을 적용했다. 종료된 대회에는 공개 정정 안내를 표시한다. v19에서는 종료된 대회의 후보 작성·미리보기·확인 후 반영·확인 후 폐기를 제공하며, 후속에서 반영 전후 감사 화면도 추가했다. v24에서는 legacy 차단 후보에 한해 명시적 해소 결정을 기록하고 반영 후에는 읽기 전용 이력을 표시한다. 정책은 기존 오프라인 측정 JSON을 가져오며 검증 근거를 화면에서 만들지 않는다.

## v19 미리보기와 명시적 반영

- 미리보기는 SQL 쓰기 없이 계산한다. 새 일반 정답, 해결 근거 변경, 후보 보고서/완료 시각 변경은 확인 해시를 무효화한다. 반영 시 같은 계산을 잠금 안에서 다시 수행한다. 전체 후보 묶음의 해시는 페이지 이동에도 같고, 화면에서는 페이지 이동이나 공개 사유 수정 후 확인을 다시 받는다.
- 검토 중 발견한 불일치를 수정했다. 같은 시각의 근거 선택은 새 행의 임의 UUID 대신 불변 출처 종류/ID로 정렬한다. 참가 기록이 누락된 제출은 미리보기와 반영 모두 거절하여 표에 없는 점수를 바꾸지 않는다. 후보 완료 시각도 확인 해시에 포함한다.
- v18 기존 감사 기록의 preview_hash는 NULL로 유지한다. 이전 기록에 검토 증거를 만들어 넣지 않는다. 기존 반영의 호환 재시도는 사유/버전이 같으면 저장된 결과만 반환하며 NULL을 바꾸지 않는다. 새 v19 반영은 해시가 필수이고 다른 해시의 재시도는 409다.
- 후보 생성은 같은 내용의 수동 재시도에 같은 requestId를 사용한다. 네트워크 오류 뒤 자동으로 반영/폐기를 재시도하지 않는다. 계정/경로 변경은 요청을 중단하고 늦은 응답을 무시한다. 생성·비교·반영 중 권한 상실은 작성 폼과 다른 비공개 이력도 정리한다.
- 백엔드 최종 집중 회귀: **78 PASS /1 환경 SKIP /28.08초**. 재채점·대회·마이그레이션·기존 워커·제품 기능을 포함한다. 마이그레이션 검사는 실제 감사 행을 생성한 뒤 이전 스키마로 만든 격리 DB를 두 번 갱신하고 원래 감사 필드/NULL 보존을 확인한다. 실제 PostgreSQL 검사는 아니다.
- 프런트 최종 전체: **264 PASS /49파일 /36.73초**, 타입 검사 PASS. 빌드 PASS(6.01초)는 최종 테스트 2건 추가 전 동일 제품 코드 기준이다. 첫 이력 집중 검사는 오래된 문구 assertion 1건이 실패했고 수정했다. 추가 권한 상실 통합 회귀의 첫 실행은 toHaveValue에 비지원 비대칭 matcher를 전달해 2건 실패했으며 실제 textarea 값 검사로 고쳤다. 제품 제한이나 테스트 시간 제한은 완화하지 않았다.
- 실제 Edge: **18 PASS /16.4초**, 320/768/1440px. 후보 작성→정책 가져오기→미리보기→확인→반영 완료 화면을 포함하며 모든 API는 합성 응답이다. 모바일/데스크톱 스크린샷을 직접 확인했고 전체 페이지 넘침 없이 비교 표만 가로 스크롤된다. 실제 DB/워커와 연결한 대회 수락을 대신하지 않는다.

## 검증 증거

- 직전 후보 처리 회귀: 58 PASS /4 환경 SKIP /22.82초.
- 초기 반영·기존 대회/작업 회귀: 51 PASS /1 환경 SKIP /28.64초.
- 확장 검사: 55 PASS /1 실패. 새 테스트가 실행 작업의 필수 payload_hash를 누락한 것이어서 테스트 데이터만 수정했다. 이후 반영 전용 14 PASS /19.00초.
- 관리자 권한/공개 정보 분리, 다른 정답 보존, 유일한 정답 취소/신규 지급, 같은 요청 재시도, 접수 시각/실행 ID 보존, 스냅샷·제출·점수판 충돌, legacy 차감 거절, 중간 오류 전체 롤백, 두 독립 SQLite 세션 동시 반영, 감사 크기 제한, 기록 삭제 후 근거 보존, 수동 지급 멱등성을 검사했다.
- SQLite/API/큐와 합성 보호 계측 실행기의 증거다. PostgreSQL 실제 경쟁, 프로세스 강제 종료, Linux 6개 런타임 성능 검증을 대체하지 않는다.
- Terra 프런트 집중 17 PASS. 주 에이전트 추가 검토로 계정/경로 변경 시 대회 화면을 즉시 초기화하고, React 키/속성에서 토큰 대신 불투명 세션 번호를 사용한다. 계정 전환 회귀도 추가했다.
- 첫 프런트 전체 검사: 245 PASS /1 기존 Monaco 파일 복사 검사 시간 초과. 같은 제한을 유지하고 작업자 수를 2로 제한한 후 전체 247 PASS /47파일 /48.32초. 이후 타입 검사의 테스트 내 미사용 인자 오류를 수정했고 타입/빌드 재검사 중이다.
- 첫 Edge 검사: 14 PASS /1 기존 320px 업로드 화면 로딩 시간 초과 /2.2분. 신규 재채점·공개 정정·권한 상실 검사는 320/768/1440px 모두 통과했으며 320/1440px 스크린샷을 직접 검토했다. 모든 API는 가로챈 합성 응답이다. 시간 제한은 늘리지 않았다.
- 전체 백엔드: 2547 PASS /414 환경 SKIP /8 subtests /4 실패 /687.02초. 실패는 B++ E/H 컴파일 20초, JavaScript A 실행 2초, Python D 실행 2초의 시간 초과다. 실패한 검사는 새 재채점 경로가 아니지만 원인이 확정되지 않았으므로 전체 통과로 기록하지 않는다. 다른 검사와 겹치지 않는 재실행이 필요하다.

## 남은 필수 작업

최종 프런트 확인: 미사용 인자 수정 후 타입 검사 PASS, 빌드 PASS(21.40초), Edge 전체 15 PASS(18.0초). 이전 업로드 로딩 시간 초과는 같은 30초 제한으로 재실행 시 재현되지 않았다. 최초 실패와 재실행 결과를 모두 남기며 원인을 특정 사용자 설정으로 단정하지 않는다.

백엔드 시간 초과 후속: 분리한 6개 검사에서 5 PASS/JavaScript D 1 FAIL(53.20초), JavaScript 단독 검사에서 G 시간 초과 1 FAIL(56.17초)였다. 한 파일의 결정적 풀이 오류라는 근거는 없었다. 빈 Node 실행 20회는 43.2–70.1ms로 모두 통과했다. 실패 시 사례 번호/입력 앞부분을 보여주는 진단만 추가했으며, 다음 JavaScript 예제 전체 검사는 같은 2초 제한으로 1 PASS(10.27초)였다. B++ E–I/Python은 앞선 분리 검사에서 통과했다. **최초 전체 실행의 4 FAIL을 지우거나 단일 전체 실행 PASS로 합산하지 않는다.** 현재 간헐 지연 원인은 확정되지 않았고 실제 Linux 런타임 정책 수락과는 별개다. 이 단계의 실행 프로세스는 모두 종료됐다.

이 문단은 v19 당시 기록이다. 큰 대회 분할 반영은 v21, 정정본 검수는 v20/v23, 과거 해결 출처 해소 절차는 v24에서 로컬 구현·검증했다. 실제 PostgreSQL 경쟁/재시작, 운영자의 실제 legacy 결정과 통지·이의 제기 절차는 여전히 남아 있다. 전체 Goal의 런타임 준비 상태/호스트 자원 안전성/6언어 실제 측정/A–J 최종 패키지와 출처·난이도·일정·J 배점·공개 정책 승인도 별도다. 로컬 재채점 검사 통과만으로 전체 완료를 선언하지 않는다.

## v20 정정본 검수 연결 (2026-09-27)

원본 문제의 승인 지문에는 테스트·정책이 포함되어 있어, 정정본에 원래 승인을 재사용할 수 없었다. 시작한 대회의 원본 편집 금지도 유지해야 한다. 따라서 정정 후보별 append-only 검수 기록을 별도 테이블에 추가했다. 수정본의 출처·지문·테스트·실행 제한 네 범주를 각각 명시적으로 승인하며, 이전 승인은 감사용 근거로만 보관한다. 테스트 자산을 바꿀 수 있도록 후보 생성 시 출처 메타데이터를 함께 고정할 수 있고, 필드 생략은 보존, null 삭제는 거절한다. 생성 이후 후보 내용은 수정하지 않는다.

- GET/POST `/api/v1/contests/{contestId}/rejudges/{batchId}/reviews`: 관리자만 접근, no-store. 고정된 후보 전체를 확인하고 정확한 후보 요청 해시/콘텐츠 지문에 승인·반려 메모를 추가한다. 클라이언트가 승인자·시각·순서를 지정할 수 없다. 동일 요청 재전송은 한 기록이며 다른 내용/대상 재사용은 충돌한다.
- 이전 출제 검수와 같은 출처 이용 근거·기준 풀이/생성기/검증기/오답 자산·언어 정책/저장 테스트 무결성 검사를 공유한다. 기록된 해시나 합성 테스트가 실제 검수/이용 허가/실측 증거를 대신하지 않는다.
- 후보 전용 `authoring-validations` POST/GET은 live 문제와 분리된 고정 정정 snapshot을 비공개 durable job으로 실행한다. 필수 언어별 accepted 증명이 후보 snapshot·출제 지문·기준 풀이·정책·테스트 hash와 정확히 맞아야만 apply가 진행된다. 이전 문제나 다른 후보의 통과 결과는 재사용하지 않는다.
- 점수 미리보기 해시에 최신 검수 이벤트를 포함한다. 반려나 재승인 후에는 기존 확인 해시가 무효다. 실제 반영은 공통 실행 잠금 안에서 네 범주의 최신 승인과 정책/테스트 근거를 다시 확인하며, 점수 변경과 같은 트랜잭션으로 정확한 승인 ID·지문·메모와 이전 근거를 감사 기록에 저장한다.
- 적용·폐기·실패 후보에는 새 검수를 추가하지 않는다. 이전 스키마의 미반영 후보는 검수 기준이 NULL이므로 폐기 후 다시 생성해야 한다. 이전 적용 기록의 승인 근거는 NULL로 유지하며 만들어 채우지 않는다. 과거 적용의 동일 재시도는 저장된 결과만 반환한다.
- 프런트는 메타데이터 편집, 후보 전체/근거 확인, 네 범주의 명시적 결정, 검수 미완료 반영 차단을 제공한다. 이전 서버 응답에 `reviewBlocked`가 없을 때에도 허용하지 않는다. 승인 저장 후 미리보기와 확인 체크를 초기화한다.

## v21 대규모 캠페인 분할과 단일 반영 (2026-09-27)

- 기존 `batchId`는 외부 API와 감사 기록에서 캠페인 ID로 유지한다. 내부에 순번·제출 수·소스 바이트·manifest hash를 가진 shard를 추가했으며, 새 항목은 정확히 한 shard에 속한다. 이전 형식의 미반영/반영 기록은 NULL 캠페인 필드를 그대로 읽고 기존 1,000건 상한으로 검증한다.
- 제출은 원래 `received_at, submission_id` 순서로 고정한다. 다음 항목을 넣으면 1,000건 또는 64 MiB를 넘는 지점에서만 shard를 닫는다. 같은 `requestId`의 정확한 재시도는 기존 캠페인과 경계를 재사용한다. 단일 소스가 shard 상한을 넘거나 캠페인이 10,000건/512 MiB를 넘으면 어떤 캠페인 행도 남기지 않고 거절한다.
- 각 manifest는 제출 ID, 원래 제출 전체 지문, 원래 판정, 언어, 접수 시각, 소스 크기/hash, 실행 계약 hash를 묶는다. 완료 시에는 후보 판정·보호 계측 보고서·완료 시각을 별도 receipt hash로 고정한다. 첫 미리보기와 실제 반영 모두 현재 제출, shard 소유권/경계, manifest, 후보 receipt를 다시 검사한다.
- 모든 항목이 완료되고 모든 shard가 `ready`일 때만 캠페인이 `ready`가 된다. 한 shard라도 `system_error`/취소이면 캠페인 전체가 `failed`이며 점수 반영 API를 사용할 수 없다. 재시작 시 아직 execution job이 없는 항목만 기존 bounded dispatcher가 이어서 배정한다.
- 미리보기·네 범주 검수·반영·감사는 캠페인 단위다. 반영은 기존 실행 잠금과 DB 트랜잭션에서 점수판 revision을 한 번만 올리고, application/점수 보정 감사 행도 캠페인당 한 번만 만든다. 공개 정정 응답에는 shard ID, 소스, 숨김 테스트를 추가하지 않았다. 관리자 화면에는 shard ID 대신 순번과 전체 진행률만 보인다.
- 로컬 집중 검증은 캠페인/반영/미리보기/검수/실제 legacy 모양 마이그레이션과 runtime marker를 포함해 **64 PASS/1 환경 SKIP**으로 기록한다. 개수 분할, 바이트 분할/정확한 경계/단일 소스 초과 전체 롤백, exact retry, shard 소유권·manifest·원래 판정·후보 결과 변조, 한 shard 실패 전체 무반영, 다중 shard 단일 application/revision을 포함한다. 프런트 전체 **296 PASS/54파일**, 타입 검사와 production build도 통과했다.
- 이 검증은 SQLite와 합성 보호 계측 runner다. 실제 PostgreSQL 행 잠금/재시작, 운영 규모의 1,001건 이상 캠페인, 실제 Linux 6언어 재채점은 여전히 외부 격리 환경에서 확인해야 한다. 운영 DB·큐·대회·배포는 변경하지 않았다.

## v24 과거 해결 출처 해소 (2026-09-27)

- legacy-only 점수는 계속 자동 차감하지 않는다. 관리자 POST는 정확한 legacy 지문과 batch 요청 해시를 요구하며, `retain_unattributed` 또는 `link_verified_receipt` 중 하나를 명시적으로 선택한다. 연결 대상은 같은 사용자·문제·배점의 기존 accepted 일반 제출 또는 대회 제출 영수증만 허용한다. 수동 출처를 새로 만들거나 원래 legacy 근거를 덮어쓰지 않는다.
- 해소 기록은 `(batch, legacy evidence)` 및 `(actor, requestId)` 단위로 append-only/멱등 저장한다. 다른 내용으로 같은 요청 ID를 재사용하면 409다. 미리보기는 해소 계획과 비밀값 없는 provenance를 해시에 포함하고, 반영은 실행 잠금 안에서 legacy/source 지문을 다시 확인한 뒤 미리 본 정확한 계획만 적용한다. 연결 영수증이 바뀌거나 legacy 점수가 달라지면 전체 반영을 거절한다.
- GET/POST `/legacy-resolutions`는 관리자 전용/no-store다. 화면은 차단된 미리보기에만 쓰기 UI를 보이고, 명시적 결정·메모·영수증 종류/ID를 받는다. 계정/경로 변경과 401/403에서 민감 상태를 정리하며, 반영 뒤에는 감사 이력만 읽기 전용으로 표시한다. 다른 사용자의 소스와 숨김 테스트는 응답/UI에 넣지 않는다.
- 백엔드 legacy 전용 **6 PASS**, 관련 확대 **123 PASS/9 조건부 환경 SKIP**, 최종 전체 **3,024 PASS/447 조건부 환경 SKIP/10 subtests/실패 0/372.40초**다. 프런트 최종 전체 **56파일/317 PASS**, 타입 검사와 production build가 통과했다. Python 모듈 구문 검사와 `git diff --check`도 통과했으며 줄바꿈 경고만 남았다.
- SQLite의 독립 세션 동시 요청, stale preview, 중복 해소, 잘못된 사용자/영수증, 독립 accepted 근거 보존, 정확한 한 번의 차감, 중간 오류 전체 롤백을 검사했다. 실제 PostgreSQL 경쟁/rolling 재시작과 운영자의 실제 출처 판단은 외부 수락 조건이다. 운영 DB·점수·배포·push는 변경하지 않았다.
