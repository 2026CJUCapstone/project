# 여섯 언어 격리 실행 검증

## 범위와 결론

2026-09-26, 기존 배포 서버의 **별도 일회용 컨테이너**에서 앱의 measured-v1 실행기를 검증했다. 최종 실행은 **23/23 PASS**, 서로 다른 단계 컨테이너 46개, 종료 후 제출 컨테이너와 작업 디렉터리 각각 0개였다. 이는 작은 고정 소스의 실행·판정 검증이며 A–J 전체 입력의 성능 수락, 실제 DB 워커 재시작, 운영 배포 검증이 아니다.

운영 DB·Redis·큐·점수판에는 접근하지 않았다. 새 이미지 다운로드, 빌드, 설치, 배포, Git push는 수행하지 않았다. 컨트롤러의 DB 설정은 메모리 SQLite이며 이 실험은 DB 세션을 열지 않는다. 실제 정책 승인이나 대회 등록도 하지 않았다.

2026-09-27 감시 시간 후속에서는 모든 모드에 고정 240초를 쓰던 호스트 감시기를 고정 입력 묶음별 내부 마감 합계와 검토된 비작업 여유 60초로 계산하도록 고쳤다. 역사적 23개 mechanics 실행은 `23×30+60=750초`였고, PID 진단을 추가한 현재 24개 mechanics/all은 `24×30+60=780초`다. B++ 단독은 150초, A–J descriptor는 520초, 79개 초안 입력은 842초, 느린 풀이 비교는 198초, B++ 진단은 168초다. 모든 값은 60–1200초에서만 허용하며, A–J 아카이브는 해당 SHA-256이 일치하지 않으면 컨트롤러를 만들기 전에 거절한다.

동일 기존 이미지로 전체 mechanics를 다시 실행해 **23/23 PASS, 46단계, 47.5초, timeout 없음**을 확인했다. 보고서에는 언어·계산 근거·실제 경과 시간·정리 전후 용량과 소유 컨테이너 최종 재탐색 결과가 들어간다. [원시 증거](evidence/judge-runtime-matrix-watchdog-r1-2026-09-27.json) SHA-256은 `8c4ddc33f2d0dd1f544f9270274d526b1ffe9c347838dc9fb23af9316aebf94c`다. 컨트롤러 1개를 정확한 소유 표식으로 제거했고 잔여 컨테이너는 0개였다. 별도 network-none/read-only 회귀에서는 timeout/증거/정리 보존을 포함해 **60 PASS**, 로컬 의존성 없는 검사는 **12 PASS**였다.

2026-09-27 현재 코드는 `pids.events:max`를 보호된 완료 기록에 넣는 v2 계약과 Python process-explosion 진단 1개를 추가해 mechanics 매트릭스를 **24개**로 확장했다. 이 변경 뒤 로컬 parser/registry/launcher/harness 회귀는 통과했지만, 새 24번째 진단과 v2 실행기는 실제 Linux/cgroup 환경에서 아직 실행하지 않았다. 위 23/23 증거는 해시가 고정된 v1 실행기의 역사적 증거이며 v2 수락 증거로 재해석하지 않는다. 사용자가 별도 격리 환경을 설정한 적은 없으므로, 이전 배포 호스트의 일회용 컨테이너 실행도 독립 staging 수락을 대신하지 않는다.

실행 전 정확한 `/tmp/webcompiler-launcher-test.<임의 식별자>` 경로, 로컬에 이미 존재하는 두 이미지 digest와 가용 용량을 검사한다. `--execute`가 없으면 실행하지 않는다. 실행 소스는 읽기 전용으로 마운트하고 한 번에 하나의 제출 단계만 실행한다. 참가자 컨테이너에는 Docker 소켓을 전달하지 않는다.

2026-09-27 현재 harness는 기본 `/var/run/docker.sock`과 `/run/docker.sock`을 거절한다. 실행하려면 별도로 구성한 Unix 소켓을 `--docker-socket`에, 그 소켓에서 읽은 `docker info --format '{{.ID}}'` 값의 SHA-256을 `--daemon-id-sha256`에 명시해야 한다. 실행할 outer harness 자체의 검토된 SHA-256도 `--harness-sha256`으로 전달한다. 심볼릭 링크·일반 파일·없는 소켓·기본 소켓으로 resolve되는 경로·식별값 불일치는 이미지 조회나 컨테이너 생성 전에 실패한다. 선택한 소켓만 컨트롤러의 `/var/run/docker.sock`으로 전달하며 보고서에는 실제 데몬 ID와 고정 입력들의 SHA-256을 남긴다. 이 검사는 별도 데몬을 설치하거나 생성하지 않으므로, 현재처럼 사용자가 그런 환경을 준비하지 않은 상태에서는 실제 실행 성공을 주장하지 않는다.

Docker에 처음 연결하기 전 앱 소스 아카이브, 실행할 verifier, 측정/slow verifier, 후보 컴파일러 보조 스크립트와 후보 소스/압축 ELF, suite별 reference archive를 모드별 allowlist와 정확한 SHA-256으로 검사한다. 파일은 심볼릭 링크가 아닌 bounded regular file이어야 한다. 임시 root와 writable work는 현재 사용자 소유·canonical·owner-only 디렉터리여야 하며, 이미 존재하는 `jobs` 경로가 있으면 내부 실행도 시작하지 않는다. 이 동일한 workspace gate는 mechanics뿐 아니라 `freshman`, draft, candidate, slow, B++ diagnostic inner verifier 모두가 공유한다. 참가자 단계의 Docker create 인자는 exact key allowlist를 사용하므로 `privileged`, host PID/user namespace, device나 임의 mount 같은 추가 옵션은 create 호출 전에 거절된다. 데몬 ID 조회가 실패하거나 기대값과 다르면 `DOCKER_HOST`도 호출 전 값으로 복원한다.

reference archive는 독립 boolean 조합으로 추측하지 않고 suite 이름으로 다음과 같이 고정한다.

| suite | reference archive |
|---|---|
| `mechanics` | 없음 |
| `freshman`, `freshman-candidate`, `bpp-diagnostic` | v1 descriptor `8dae6743dbf815bb58c310c0111f5c18bf3070508c8cda4fe485862800e633ab` |
| `freshman-draft`, `freshman-draft-candidate` | draft v2 `053472836c1e7fe5b2652cadb2697dc88046cb16dbba1c6af0ec4ce8b9d18ebc` |
| `freshman-slow` | draft v2 + F/I/J slow sources `a90de99a98085194e3d6cd371f76c74fa3727efc60c8f31c1f35aec9fcc596a0` |

candidate suite는 compiler 입력만 추가하며 같은 등급의 reference archive를 바꾸지 않는다. 느린 풀이 비교와 candidate overlay의 결합은 지원하지 않고 전송 전에 거절한다. archive 종류가 suite와 다르면 첫 Docker 호출 전에 실패한다.

## 최초 실패와 수정

최초 전체 검사: **21 PASS /2 FAIL**. B++ 정상 코드의 정답·오답 검사 모두 컴파일 오류가 났다. 별도 B++ 진단은 **1 PASS /2 FAIL**이었고, 컴파일 오류 출력은 `/tmp/bpp_run_*` 생성 시 읽기 전용 파일 시스템 오류였다. 설치된 B++ 명령이 `TMPDIR=/work`와 무관하게 `/tmp`를 사용했다. 사용자 설정 변경을 원인으로 볼 근거는 없다.

수정은 B++ **컴파일 단계에만** 기존 `tmpBytes`를 `/work`와 `/tmp`로 나누어 제공한다. 합계는 원래 한도와 같고 두 마운트 모두 4 KiB 배수다. 실행 단계와 다른 언어에 쓰기 가능한 `/tmp`를 추가하지 않았다. 최소 8 KiB 및 페이지 정렬 조건은 런타임 등록부에서 검사한다.

마운트 의미가 달라졌으므로 B++ 도구 프로필을 `bpp-native-o1-v2-tmp-split`로 구분했다. 이전 v1 영수증을 새 의미로 조용히 실행하지 않는다. 기존 정책은 새 프로필에 대한 명시적 측정·검토를 거쳐야 하며 이 실험이 그 승인을 대신하지 않는다.

## 안전 한도·정리

컨트롤러 384 MiB/0.5 CPU, 제출 단계 최대 512 MiB/1 CPU, swap 추가 허용 없음, 네트워크 없음, 읽기 전용 루트다. 이미지 확인용 컨테이너는 512 MiB/0.5 CPU로 제한했다. mechanics 한 검사의 외부 대기 한도는 30초이며, 전체 컨트롤러는 위의 고정 모드별 150–842초 감시 시간을 쓴다. mechanics 단계 컨테이너 최대 80개다. 호스트 실행 전 최소 여유 RAM 2 GiB/디스크 4 GiB를 요구했다.

최종 실행의 호스트 가용 메모리는 6,628,626,432→6,601,211,904 bytes, 디스크 여유는 4,969,037,824→4,967,677,952 bytes였다. 이 전후 차이는 호스트 전체의 관찰이며 제출 하나의 사용량이나 부하 시험 결과가 아니다.

소유 표식으로만 테스트 컨테이너를 정리했다. 이후 세 임시 디렉터리 `Y1UdIir4`, `zbMF7o5d`, `8HmA4aeD`의 실제 경로와 크기를 재확인한 뒤 해당 경로만 제거하고 부재를 확인했다. 테스트 컨테이너 0개, 기존 basic 서비스 7개 healthy 상태를 다시 확인했다. 로컬 소스·스크립트·최종 아카이브는 보존했다. 세 실행의 원시 JSON은 당시 도구 출력에 남았지만 별도 JSON 파일로 저장하지 않았으므로, 이 문서는 그 출력을 정리한 기록이며 원시 로그 파일이 있다고 주장하지 않는다.

## 강화한 검사 재실행과 원시 증거

Terra의 읽기 전용 검토에서 판정 이름만 검사하는 약점이 발견됐다. 주 에이전트가 다음을 추가하고 실제 동일 이미지에서 다시 실행했다.

- 정답 3단계, 오답 2단계, 구문 오류 1단계, 자원 실패 2단계를 정확히 요구한다. 모든 언어/사례의 조합과 중복·누락도 검사한다.
- CPU TLE는 CPU 한도 이상이면서 wall 한도 미만, wall TLE는 반대 조건을 확인한다. MLE는 `oomKills>=1`, OLE는 수집된 정확한 출력 한도, exit 137은 실제 종료 코드와 OOM 부재를 검사한다.
- Docker 생성 **이전**에 이미지·실행 명령·읽기 전용 루트·호스트 마운트·네트워크·CPU·메모리/swap·PID·임시공간·capability·IPC/cgroup·로그·파일 수 한도를 확인한다.
- 하나의 제거 실패가 다른 소유 컨테이너 정리를 생략하지 않도록 정리를 시도한 뒤 실패를 합산한다. 소유권이 다른 컨테이너는 제거하지 않는다.
- 원시 출력, 이미지·소스·검사 스크립트 해시, 실제 도구 버전과 호스트 전후 여유를 저장한다. 최초 세 실행의 기록은 계속 도구 출력뿐이며 소급하여 원시 파일을 만들지 않았다.
