# 대용량 채점 데이터 저장·접수·실행 연결

작성일: 2026-09-26. 상태: 문제·대회·접수·큐·워커·관리자 화면 연결 구현, 격리 SQLite/ASGI 통합 및 실제 Linux Python 9 MB 입력 검사 통과. 전체 여섯 언어 수락, 실제 PostgreSQL 워커 복구, 운영 프록시 적용은 아직 검증하지 않았다. 운영 등록·배포는 하지 않았다.

## 필요한 이유와 범위

지문 C는 숫자 100만 개, E는 영문자 100만 개, I는 1000×1000 상태를 허용한다. 입력은 약 1~9 MB가 될 수 있지만 기존 private package는 케이스당 input+expected 1,000,000 bytes, 전체 4,000,000 bytes까지만 허용한다. durable queue도 전체 JSON을 2,000,000 bytes로 제한한다. 제한을 모두 크게 올려 제출마다 같은 테스트를 복제하는 대신, 원본 텍스트를 한 번 저장하고 불변 해시를 참조하는 경로를 준비한다.

관리자 전용 저장·조회, 해시/길이/인코딩 검증, 저장량 상한과 반복 업로드의 멱등성을 구현했다. 파일 경로나 URL을 받아 서버에서 읽지 않는다. 아래 연결은 로컬 소스 변경이며 운영 DB·대회·문제·제출·점수는 변경하지 않았다.

`models/judge_test_manifest.py`와 `services/judge_test_manifest.py`의 엄격한 숨김 참조를 문제 작성, 비공개 패키지, 대회 고정 사본, 정책 지문, 접수, 자원 예약, 워커의 케이스별 복원에 연결했다. 저장 참조는 측정 정책이 있는 채점 경로에서만 실행하며, 구형 실행기에 조용히 넘기지 않는다.

## 계약

- `PUT /api/v1/admin/judge-test-data/{64자리 소문자 SHA-256}?byteCount=N`
  - 인증된 관리자만 사용한다. 인증/역할 확인은 요청 본문을 읽기 전에 수행한다.
  - 원본 UTF-8 본문만 받는다. Content-Type은 `text/plain` 또는 `application/octet-stream`, Content-Encoding은 생략/identity만 허용한다.
  - 0~16 MiB, 정확한 바이트 수와 원본 바이트의 SHA-256이 일치해야 한다. Content-Length가 있으면 선언 크기와 일치해야 한다. chunked 전송도 누적 상한을 검사한다.
  - 프로세스마다 수신/저장 중 업로드를 한 개만 허용한다. 두 API 프로세스라면 최대 두 개이므로 이것을 전역 한도라고 부르지 않는다. 총 수신 제한은 30초다. 추가 요청은 429/Retry-After로 거절한다.
  - 결과: `digest`, `byteCount`, `encoding: utf-8`, `replayed`. 원본 내용은 반환하지 않는다.
- `GET /api/v1/admin/judge-test-data/{64자리 SHA-256}`
  - 관리자 전용 메타데이터만 반환한다. DB에서도 압축 본문 열을 조회하지 않는다. 공개 다운로드·리스트·삭제·덮어쓰기 API는 없다.
- 성공 응답은 `Cache-Control: no-store`다. 관리자 감사 이벤트에는 경로/행위만 남기고 본문을 기록하지 않는다.

## 보관·복구·자원 경계

새 `judge_test_data` 테이블은 해시를 기본 키로 쓰고 바이트 수·zlib 압축 본문·작성자·시각을 저장한다. v16 초기화 버전은 `20260926_judge_test_data_v16`이다. 기존 제출·점수·정책·v15 표식은 보존한다.

`JUDGE_TEST_DATA_STORE_MAX_MB`는 압축 전 총량(기본 512 MiB, 허용 16~8192), `JUDGE_TEST_DATA_STORE_MAX_OBJECTS`는 최대 행 수(기본 10000, 허용 1~100000)다. 작은 파일을 많이 올려 메타데이터가 무한 증가하는 것도 막는다. 값은 실제 운영 디스크·DB 백업/복제 예산 확인 후 별도로 정해야 하며 현재 서버 설정을 변경하지 않았다.

압축은 DB 전역 잠금을 잡기 전에 끝낸다. 중복 확인·전체 총량·삽입은 기존 DB 실행 잠금으로 직렬화하고 같은 트랜잭션에서 처리한다. 네트워크 수신 중 DB 쓰기 잠금을 잡지 않는다. 같은 데이터를 다시 올리면 기존 행을 반환하며, quota가 가득 차도 정확한 재시도는 허용한다. 기존 저장 내용이 손상됐으면 조용히 덮어쓰지 않고 거절한다.

읽을 때는 압축 본문 크기, 선언한 원본 길이, 제한된 압축 해제, 스트림 완결/뒤따르는 데이터 부재, UTF-8, 전체 해시를 다시 확인한다. 압축 폭탄이나 잘린/변경된 데이터가 정상 테스트로 사용되지 않도록 한다. 문제 작성·정책 승인·대회 저장에서는 무결성을 검사하고, 새 접수는 작은 메타데이터만 확인한다. 워커는 실제 실행 전에 케이스별 무결성을 다시 확인한다.

클라이언트가 저장 중 연결을 끊어도 백그라운드 저장 스레드가 끝나기 전에 업로드 슬롯이나 DB 세션을 반환하지 않는다. 완료됐는지 불확실하면 동일한 바이트/해시로 재시도한다. 아직 참조 추적·GC가 없으므로 임의 삭제로 공간을 회수하지 않는다.

## 참조·복원 도우미의 범위

숨김 참조는 `kind: stored-v1`, `inputRef`, `expectedOutputRef`로 구성한다. 각 참조에 정확한 SHA-256, 엄격한 정수 `byteCount`, `encoding: utf-8`을 둔다. URL·파일 경로·다른 인코딩·음수/float/bool 크기·알 수 없는 키·인라인 내용과 참조 혼합·동일 해시의 상충하는 크기를 거절한다. 공개 예제에는 참조를 허용하지 않는다.

정규화와 정책 지문은 기존 인라인 형식을 그대로 유지한다. 공백과 줄바꿈을 바꾸거나 인라인 kind 필드를 주입하지 않으며 기존 `test_suite_hash`와 동일함을 회귀 검사했다. 참조 해시를 바꾸면 새 지문도 달라진다. 대회 사본과 이미 접수된 작업에는 기존 참조가 남으므로 원본 수정이 진행 중 제출을 바꾸지 않는다.

도우미의 최대 범위는 200케이스, 데이터 하나당 16 MiB, 전체 입력+정답의 선언된 원본 크기 256 MiB다. 중복 사용한 데이터도 실행 횟수만큼 전체 크기에 센다. 이것은 전체 Job deadline·메모리·디스크 예약의 대체 기준이 아니다.

`verify_reference_metadata`는 중복을 제거한 최대 400개 참조의 해시/크기 열만 한 번 조회한다. 압축 본문은 읽지 않으므로 저장 데이터가 손상되지 않았다는 증거는 아니다. `materialize_case`는 요청한 케이스만 읽고 길이·압축 스트림·UTF-8·내용 해시를 확인한다. 누락/변조를 빈 입력으로 치환하지 않는다. 워커는 짧은 DB 세션을 종료한 뒤 실행기를 호출하고, 다음 케이스 복원 전에 이전 데이터 참조를 해제한다. 취소 중에도 DB 읽기 스레드 종료를 기다린다. 숨김 정답은 호스트에서만 비교하며 실행 컨테이너에는 현재 입력만 준다.

저장 참조가 있는 접수에는 `testDataBufferBytes = 12 × max(케이스 입력+정답 원본 bytes) + 131072`를 고정한다. 기존 단계 메모리 최대값에 이 값을 더해 `reservationBytes`를 구성하고, 스케줄러는 기존 작업별 외부 여유분도 추가한다. 복원·UTF-8·압축/원본 버퍼를 위한 보수적 예약이며 실제 최악 RSS를 측정했다는 뜻은 아니다. 순차 실행이므로 전체 케이스 크기를 동시에 메모리에 예약하지 않는다. 필드와 선언 크기가 변조되면 실행을 거절한다. 인라인 전용 영수증에는 새 필드를 붙이지 않는다.

## 관리자 화면·CLI·전송 경계

문제·대회 편집 화면은 기존 저장 참조를 해시·크기로 표시하고 내용은 내려받지 않는다. 두 UTF-8 파일을 선택한 뒤 업로드 버튼을 눌러야 전송하며, 양쪽 영수증이 일치해야 목록에 추가한다. 부분 실패 시 목록은 그대로 두고 미참조 저장 데이터가 남을 수 있다고 안내한다. 계정/편집 대상 변경·화면 종료 후 늦게 도착한 응답은 반영하지 않는다. 업로드 중 전체 저장은 막는다.

`scripts/upload_judge_test_data.py`는 기본적으로 파일의 해시·길이만 오프라인 계산한다. 명시적인 `--apply --api-base`가 있을 때만 관리자 토큰으로 전송하며 리다이렉트·자동 재시도는 하지 않는다. 비공개 패키지는 미리 올린 참조를 보존한다. 인라인 한 개 1 MB/합계 4 MB의 모델 상한과 별개로, 패키지 정규 JSON은 일반 API와 같은 512 KiB 이하로 제한한다. 이전 6 MB 표기는 실제 프록시 전송 경계와 달라 폐기했다.

프런트·edge·API proxy·외부 TLS location 소스에는 관리자 업로드 경로만 16 MiB/요청 버퍼링 해제/상위 재전송 금지를 추가했다. 일반 API 512 KiB는 유지한다. 내부 프록시는 노드별 IP 2개/전체 8개 연결 상한을 두며, API의 프로세스별 1개 업로드 한도도 유지한다. 이 연결 상한은 여러 호스트를 합친 전역 한도가 아니다. API proxy membership 인증 단계도 새 경로에 유지한다. 렌더링 회귀와 실제 격리 Nginx 문법 검사는 통과했고, 전체 프록시 HTTP 경로는 별도 검증이 필요하다.

## 연결 검증과 실제 Linux 범위

- 로컬 SQLite/ASGI 약 9 MB 업로드→문제 생성→작은 접수 payload→새 워커 인스턴스 복원→점수 반영을 검사했다. 실행기는 합성 보호 기록을 반환한다. 손상된 저장 데이터는 기존 큐 정책대로 재시도 후 시스템 오류가 되며 득점하지 않는다.
- 대회 날짜 변경 후 고정 사본 유지, 원본 변경 후 기존 접수 재시도 보존, 미리 올린 참조의 private import 멱등성, 공개 응답의 숨김 내용 비노출, 두 작업의 메모리 예약 경쟁을 검사했다.
- 실제 Linux 격리 SQLite 저장→복원→Python 실행기는 9,000,008 bytes 입력/310 bytes 숨김 manifest로 통과했다. Python 코드는 입력 길이를 출력하는 연결 검사이며 C 정답 풀이 성능 검증은 아니다. 컴파일 1회/새 실행 컨테이너 2개, 단계 입력 회수, 잔여 테스트 컨테이너·작업 디렉터리 0개를 확인했다.
- 실제 대입력 실행 CPU 26,046 μs, wall 27,553,094 ns, peak 18,944,000 bytes, OOM 0. 컨트롤러는 384 MiB/0.5 CPU/48 PID, 실행 단계는 128 MiB/1 CPU로 제한했다. 사용 이미지 `sha256:d7ab3494aad02142fe7fc4abee8175283a2ce68e57cfc7bb24da034753065930`, Python 3.12.3, launcher `sha256:908bb710244512ea3f655831a7aa84b4fb5d6ec370cd32e558f14944fbc0e505`.
- 원격 임시 루트 `/tmp/webcompiler-launcher-test.qX7EwpOp`를 확인 후 제거했다. 운영 서비스·DB·큐·설정은 변경하지 않았다. 실행 전 기본 서비스 7개 healthy, 설치/이미지 pull/배포 없음.
- 실제 Edge 320/768/1440 px에서 12개 검사가 통과했다. 업로드·검수·측정 표시를 포함하되 API는 모두 가짜 응답으로 격리했다. 실제 관리자 로그인/운영 업로드 검증이 아니다.

## 실행 단계 입력 파일 정리 보완

기존 measured 실행기는 케이스별 마운트는 분리했지만 해당 입력 파일을 제출 종료 때까지 보관했다. 큰 입력을 200번 실행하면 호스트 디스크 사용량이 누적될 수 있어, 컨테이너 삭제와 출력 읽기 종료가 확인된 뒤 그 단계의 정확한 input/empty 디렉터리만 정리하게 했다.

기존 공통 컨테이너 제거 도우미는 Docker 오류를 무시하는 동작이 있었으므로 measured 경로에서는 이를 사용하지 않는다. fenced cleanup이 거절되거나 삭제 결과가 불확실하면 다음 케이스를 시작하지 않는다. 해당 lease 작업 디렉터리도 남겨 기존 복구·회수 경로에서 처리하게 한다. 정확한 컨테이너가 이미 없다는 NotFound는 정상 정리로 취급한다. 최종 성공 조건은 별도로 전체 claim 컨테이너 부재 확인을 요구한다.

호스트 파일의 권한을 변경하는 작업도 삭제와 같은 lease guard 안에서 수행한다. 컨테이너 삭제 직후 디렉터리 정리 권한을 잃은 경우에는 입력 파일을 writable로 바꾸거나 뒤늦게 삭제하지 않는다. 정리 대상은 해당 작업 디렉터리 자체 또는 바로 아래의 생성된 단계 디렉터리로 한정하고, 예상하지 못한 symlink가 있으면 거절한다. 후속 집중 회귀는 **92 PASS / 3 환경 skip / 8.94초**다.

로컬 모의 컨테이너에서는 정상 삭제·이미 삭제됨·Docker 실패·소유권 상실을 재현했다. 실제 격리 서버의 작은 Python 1회 컴파일/2회 실행에서도 **각 단계 직후 input/empty 디렉터리 0개**를 확인했다. 이 실험은 대용량 참조 채점이나 실제 DB 워커 재시작 검증이 아니다.

## 검증

로컬 SQLite/ASGI에서 UTF-8 문자 중간 청크 분할, 빈 데이터, 16 MiB 경계/초과, C의 약 9 MB 실제 최대 입력 저장/재조회, 잘못된 해시/인코딩/길이, 압축 손상/추가 데이터/과대 압축 해제, 중복·서로 다른 세션의 동시 등록, 총량/행 수 quota, 인증 전 본문 미수신, 타임아웃·취소 중 저장 완료 대기, 관리자 외 접근 거절, 반복 초기화를 검사한다. 실제 PostgreSQL 경쟁과 리버스 프록시를 통과한 업로드는 별도 미검증이다.

최초 테스트에서 큰 bytes 파라미터가 지나치게 긴 pytest ID로 만들어져 Windows 임시 경로 생성이 실패했다. 테스트 ID를 짧게 명시해 수정했고 저장소 검증을 완화하지 않았다.
