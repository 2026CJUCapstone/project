# 격리 실행기 검증 — 2026-09-26

운영 배포·DB·큐·대회 등록 없이 사용자가 허용한 별도 컨테이너에서 수행했다. 아래 결과는 실행기 동작 검증이며, 앱 전체 채점 또는 6개 언어의 제한값 승인 결과가 아니다.

## 환경 및 결과

- Linux 6.8.0-111, cgroup v2. 기존 이미지 `sha256:d7ab3494aad02142fe7fc4abee8175283a2ce68e57cfc7bb24da034753065930`만 사용. 이미지 빌드/설치 없음.
- 순차 실행, 컨테이너별 96 MiB/1 CPU/PID 16, swap 없음, 네트워크 없음, 루트 파일시스템 읽기 전용. 외부 15초 제한.
- 부모 PID 1만 KILL/SETGID/SETUID 보유. 자식은 UID/GID 65534. 보고서는 자식 출력이 아닌 부모의 보호된 경로에서 수집.
- 모든 사례에서 프로세스 트리 회수 확인. 종료 후 부모만 남은 상태에서 보고서를 수집하고 테스트 컨테이너 제거.

## 발견 및 수정

첫 두 정상 실행은 `docker cp`가 실행 중인 tmpfs의 완료 파일을 찾지 못해 수집이 실패했다. 제한을 완화하지 않고, 부모 전용 attach 완료 신호를 받은 뒤 고정된 읽기 명령으로 수집하도록 변경했다. 채점 도중 exec로 polling하지 않아 관측용 프로세스의 CPU가 제출 측정에 섞이지 않는다.

CPU는 부모의 관측 비용을 포함한 컨테이너 누적 CPU이며, peak 메모리는 부모와 출력 tmpfs까지 포함한다. 아직 실제 정답/오답의 반복 측정과 안전 여유값 승인이 필요하다.

이 표는 최초 7사례 성공 당시의 소스 결과다. 컴파일 산출물 준비와 umask 변경 후에도 7사례 전부 재실행하여 통과했다. 재실행 MLE의 `oomKills=1`, `peakMemoryBytes=100663296`, OLE의 출력 1024 bytes, CPU/Wall TLE와 프로세스 트리 회수를 확인했다. 런타임 등록부가 없으면 measured-v1을 실행하지 않으며 예전 실행기로 조용히 대체하지 않는다.

## 실제 앱 어댑터 연결

`scripts/run_isolated_measured_pipeline.py` → `scripts/verify_measured_pipeline.py`로 현재 `DockerCompilerRunner`, `MeasuredSubmission`, `judge_code`를 실행했다. DB는 in-memory SQLite URL만 설정하고 초기화/세션/API/큐 호출은 하지 않았다. 이미 존재하는 위 이미지의 Python 의존성을 사용한 별도 컨트롤러(256 MiB/0.5 CPU/네트워크 없음)와 순차 자식 컨테이너(128 MiB/1 CPU)만 사용했다. Docker 소켓은 신뢰된 컨트롤러에만 연결하고 제출 컨테이너에는 연결하지 않았다.

최종 재실행은 Python 3.12.3, 실행기 해시 `sha256:908bb710244512ea3f655831a7aa84b4fb5d6ec370cd32e558f14944fbc0e505`에서 통과했다. 테스트 등록부는 운영 등록부가 아니며 종료 시 삭제한다.

| 컴파일 1회 | 39176 | 35702515 | 12091392 | 0 | exit 0 |

- 매 케이스 `/work`의 이전 파일 부재 및 원본 `/source` 미노출 확인.
- `/artifact/main.pyc` 수정 차단. 추가 writable `/dev/shm`으로 임시공간 상한을 우회하지 않도록 IPC `none` 사용 및 실제 쓰기 차단 확인.
- 일반 Docker 이미지의 healthcheck와 init을 명시적으로 끄고 private cgroup namespace를 요구한다.
- 숨김 결과 미노출, 컴파일 1회/서로 다른 케이스 컨테이너 2개, 잔여 제출 디렉터리/자식 컨테이너 0개 확인.
- 최초 앱 시도는 보호 검사에서 `PermissionError`만 예상했으나 실제 읽기 전용 마운트는 `EROFS`를 반환해 실패했다. 보호를 완화하지 않고 검사에서 EROFS/EACCES/EPERM만 인정하도록 수정했다. 이후 세 번의 실제 연결 검증이 통과했다. 위 표는 실행기 해시 고정, `/dev/shm` 차단, Docker 연결/ping/image 확인의 비동기 처리·세션당 연결 재사용/닫기를 포함한 마지막 실행이다.

마지막 컨트롤러 실행 전후 RAM 가용량 6573613056 → 6634131456 bytes, 디스크 가용량 4894285824 → 4893401088 bytes. 임시 소스 복사본을 포함한 4개 자체 테스트 디렉터리를 정확한 경로 확인 후 삭제했고, 세 종류의 테스트 소유 라벨에 남은 컨테이너가 없음을 확인했다. 기존 운영 기본 서비스 7개 모두 healthy다. 삭제한 것은 재생성 가능한 테스트 사본뿐이며, 소스와 검증 기록은 로컬 저장소에 유지했다.

로컬 회귀는 반복 취소 시 백그라운드 파일 수집 완료 후 정리, 늦게 반환된 attach stream 닫기, tar traversal/link/device/중복/충돌/용량 초과/기존 호스트 파일 덮어쓰기 거부, 명령·마운트·이미지 고정, 접수 시 고정한 deadline 적용을 검사한다. 실행기 해시도 정책 지문/접수에 고정하여, 등록부를 새 버전으로 바꿔도 옛 제출을 새 실행기로 묵시적으로 재해석하지 않는다. 통신·전체 작업 watchdog은 시스템 오류이며, 참가자 TLE는 신뢰된 단계별 CPU/wall 증거로만 판정한다.

## 남은 검증

최종 로컬 전체 회귀: backend **2345 PASS/409 환경 skip/8 subtests**, 198.75초. frontend **40파일210 PASS**, 타입 검사/빌드(16.69초) 통과. 새 격리 SQLite 파일을 사용했고, skipped를 실제 PostgreSQL/런타임 통과로 계산하지 않았다. 연결 처리 보완 후 실제 Python smoke도 다시 실행했다.

Python의 위 연결 확인은 여섯 런타임 전체, 실제 워커/DB lease 복구, 악성 제출의 모든 공격면, 실제 10회 이상 기준 측정, 관리자 공개/등록부 준비 상태, 정책별 성능 승인, 사용자별 접근 제어 E2E를 대체하지 않는다. 이 항목들과 재채점·출처 검수·비공개 import·B++ 풀이 등 기획의 나머지 구현은 미완료다. per-case resource report의 영속 집계도 후속 작업이다. 운영 등록부와 공개 정책을 자동 생성하거나 승인 완료로 표시하지 않았다.

추가 운영 승인 조건: 외부 수집 버퍼/산출물/문자열 변환을 포함한 워커 메모리 overhead 실측, 고정 toolchain ID의 명령·산출물 8 MiB/파일 수 512 계약 변경 시 버전 관리, 수집 중 메모리 실패/전송 지연/컨테이너 제거 실패 및 재시작 경쟁 검증. 현재 예시 overhead 32 MiB는 모든 최대 출력 조합에서 충분하다고 검증된 운영값이 아니다. 실제 six-runtime 패키지 측정 전에 사용할 수 있는 배포 설정으로 제시하지 않는다.

다언어 수락에서 추가로 확인·보완할 사항: 현재 산출물 경로 검증은 ASCII 이름만 허용하므로 Java의 Unicode 클래스 파일 지원이 필요하다. 감독기 자체가 OOM으로 사망하거나 OOM kill 없이 메모리 할당이 실패하는 경우의 증거/판정도 추가 검증 대상이다. 현재 기록 부재는 시스템 오류로 안전하게 중단하지만 모든 메모리 실패를 MLE로 판정했다고 주장하지 않는다.
