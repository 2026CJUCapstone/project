# 언어별 시간·메모리 제한: 공식 자료 비교와 적용안

확인일: 2026-09-26
상태: 정책·snapshot·실행기·UI 구현, 최종 운영값·현재 전용 환경 반복 측정 미완료
연결: [신입생 대회 기획안 6절](freshman-contest-plan-2026-09-26.md#6-언어별-자원-제한-정책)

## 1. 결론

언어별 제한을 다르게 설정하는 기능은 필요하다. 다만 타 사이트의 시간 배수와 메모리 숫자를 묶어서 그대로 가져오지는 않는다.

- 시간: 문제별 기본 시간과 런타임별 보정값을 지원하되, 출제 검수 후에는 **문제 × 런타임 버전별 절대 제한**으로 확정한다.
- 메모리: 시간 배수와 독립적으로 결정한다. 런타임·자료구조·자식 프로세스를 포함한 실제 사용량을 기준으로 한다.
- 공개 전 여섯 언어의 기준 풀이를 실행해 최종 제한을 고정하고 참가자에게 표시한다.
- 기존 초안의 Python 3배+0.2초, Java 2배+0.5초, JavaScript 2배+0.3초와 256/512MiB를 운영 기본값으로 확정하지 않는다. 공식 사이트의 권장값도 아니었다.

## 2. 공식 자료에서 확인한 내용

### AtCoder

- ABC428 A에는 문제 제한이 **2초 / 1024MiB**로 표시된다. 이것은 그 문제의 표시값이지 모든 문제의 기본값이나 언어별 배수 표가 아니다. [ABC428 A](https://atcoder.jp/contests/abc428/tasks/abc428_a?lang=en)
- 2025-10-18 ABC428부터 적용한 새 채점기는 메모리 한도 초과 시 실행을 강제 종료하며, TLE/MLE 결과에 한도를 넘었다는 표시를 제공한다. [공식 새 채점기 공지](https://atcoder.jp/posts/1579)
- 언어 테스트 대회에는 언어별 메모리 사용량과 MLE 동작을 점검하기 위한 별도 문제가 있다. 운영 전 다양한 언어로 실행 환경을 검증하는 접근을 참고한다. [Language Test 202505](https://atcoder.jp/contests/language-test-202505?lang=en)
- 확인한 공개 자료에서는 모든 대회에 공통인 Python/Java 시간·메모리 보정 공식을 확정하지 못했다. “AtCoder도 Python은 무조건 몇 배”라고 적지 않는다. 배수 설명을 찾지 못했다는 사실만으로 보정이 전혀 없다고 단정하지도 않는다.
- 언어 목록은 특정 업데이트 시점의 버전 자료다. 이를 우리 런타임의 동일성이나 최신 배포 버전의 증거로 쓰지 않는다. [2025/10 언어 목록](https://img.atcoder.jp/file/language-update/2025-10/language-list.html)

현재 원본 Help 주소는 조사 환경에서 접근하지 못했다. 아래는 **2026-04-18 보존본**이며 2026-09-26 현재 설정을 보장하지 않는다. 원본 운영자의 문서를 보존한 자료이지 제3자의 경험담이 아니다.

[BOJ 언어 정보 — 2026-04-18 보존본](https://web.archive.org/web/20260418193203id_/https://help.acmicpc.net/language/info)

BOJ는 일부 문제·언어에는 이 일반 보정값 대신 문제에 표시한 별도 규칙을 쓴다고 안내한다. 시간 누적 문제도 따로 존재한다. 따라서 BOJ의 모든 문제를 동일한 산식·케이스별 시간으로 해석하지 않는다. [시간과 메모리 — 같은 날짜의 보존본](https://web.archive.org/web/20260418193235id_/https://help.acmicpc.net/judge/time-and-memory)

우리 기획에는 **시간/메모리 각각 배수+추가량, 문제별 덮어쓰기**를 지원할 근거로 반영한다. 원문 표기의 MB를 우리 MiB/bytes와 확인 없이 동일시하지 않는다. 표의 런타임 옵션이나 과거 버전을 우리 실행기에 그대로 복사하지 않는다.

### Kattis — 시간 단위와 판정 참고

공식 지원 문서는 입력 세트별 총 CPU 시간을 측정한다고 설명한다. 스레드를 늘린다고 시간 예산이 늘지 않는다. 메모리 초과가 항상 MLE로 나타나는 것도 아니며, 할당 실패 뒤 비정상 종료로 RE가 될 수 있음을 설명한다. [가능한 판정](https://support.kattis.com/support/solutions/articles/79000141261-list-of-possible-judgements)

컴파일/문법 검사 후 케이스마다 프로그램을 새로 실행하고 케이스별 제한을 적용한다. 이 문서에서 언어별 시간·메모리 보정표는 확인하지 못했으며, 모든 Kattis 설치에 보정이 없다는 뜻으로 확대하지 않는다. 두 문서의 표시 수정일은 2023-12-04다. [채점 과정](https://support.kattis.com/support/solutions/articles/79000141262-how-judging-works)

### DOMjudge — 구현 구조의 주요 참고

문제별 제한에 언어의 시간 계수를 곱하는 구조를 지원한다. CPU 시간을 중심으로 제한하고 wall clock도 감독한다. 판정 기준과 강제 종료까지의 여유인 overshoot는 구분된다. **여유 시간 안에 종료했다고 원래 제한을 넘긴 풀이를 AC로 만드는 구조가 아니다.** [DOMjudge 9.0 judging](https://www.domjudge.org/docs/manual/9.0/judging.html)

출제자 풀이를 실제로 채점하고, 가장 느린 정답과 가장 빠른 시간 초과 풀이를 비교하도록 안내한다. 가장 느린 정답의 약 2배를 시간 제한으로 삼는 경험칙도 제시하지만, 모든 문제에 보장되는 공식은 아니다. [Testing jury solutions](https://www.domjudge.org/docs/manual/9.0/config-basic.html#testing-jury-solutions)

메모리는 JVM 같은 실행 환경까지 포함한다. 컴파일·출력 비교용 제한은 참가자 프로그램 실행 제한과 별도로 둔다. 문서의 JVM 메모리 근삿값이나 기본값은 우리 Java 버전에서 측정한 값이 아니다. [Configuration reference](https://www.domjudge.org/docs/manual/9.0/configuration-reference.html)

실제 할당 메모리를 측정하는 데 cgroup을 이용하고, JVM의 메모리 부하를 측정하는 도구도 설명한다. 가상 주소 예약량과 실제 메모리 소비를 혼동하지 않는 근거로 참고한다. 조회한 경로는 9.0 문서이며 페이지 표시는 9.0.2DEV/37f0bbdf0이다. [Judgehost installation](https://www.domjudge.org/docs/manual/9.0/install-judgehost.html#linux-control-groups)

## 3. 우리 플랫폼의 시간 정책

아래는 **자체 설계 제안**이며 위 서비스의 규칙을 그대로 재현하는 명세가 아니다.

### 3.1 측정 시작점

Codeforces 사례를 실험 후보로 활용한다. 확정되지 않은 추가 0.2/0.3/0.5초는 제거한다.

| 언어 | 실험용 기본 시간 배수 | 근거·주의 |
| --- | ---: | --- |
| C | 1.0 | 자체 비교 기준, 실측 필요 |
| C++ | 1.0 | 자체 비교 기준, 실측 필요 |
| B++ | 1.0 | 임시 비교 출발점만 의미. C++와 같은 성능을 보장하지 않음 |
| Python | 5.0 | 위 Codeforces의 Python 3 사례, 실제 인터프리터로 재측정 |
| Java | 1.5 | 위 Codeforces의 Java 사례, 버전·실행 옵션별 재측정 |
| JavaScript | 3.0 | 위 Codeforces의 Node.js 사례, 실제 Node 버전으로 재측정 |

예를 들어 기본 2초의 단순 계산 후보는 C/C++/B++ 2초, Python 10초, Java 3초, JavaScript 6초다. **이 숫자를 신입생 대회의 확정 제한으로 사용하지 않는다.** PyPy를 지원하지 않는다면 PyPy의 3배를 Python에 적용하지 않는다.

### 3.2 확정 절차

1. 기본 시간 B, 런타임별 계수 F, 기동 시간 최소 여유 S를 측정용 입력으로 둔다.
2. 초벌 후보는 max(B × F + A, S)로 계산한다. A는 근거를 기록한 추가 시간이며 기본 0으로 시작한다. BOJ형 후보를 비교할 때만 위 보존본의 추가 시간을 입력할 수 있다. S는 실제 측정한 기동 여유이며 근거 없는 고정 추가 시간이 아니다. Codeforces형과 BOJ형 계수를 서로 중첩하지 않는다.
3. 문제별·언어별로 여러 정상 풀이와 대표적인 느린 풀이를 같은 테스트에서 비교한다. 최종 CPU 시간은 가장 느린 정상 풀이의 약 2배를 검토 출발점으로 삼되 최소 여유와 측정 편차를 함께 확인한다.
4. 정상 풀이와 배제하려는 느린 풀이의 실행 시간이 겹치면 제한만 억지로 줄이지 않는다. 문제 조건·테스트·언어별 설정을 재검토한다.
5. 기동·JIT·GC는 실행 시간에 포함한다. 이미 측정된 정상 실행 시간에 기동 비용을 또 더하지 않는다.
6. 공개 시 최종 cpu_ms와 wall_ms를 절대값으로 저장한다. 판정 시 전역 배수를 다시 곱하지 않는다.

CPU와 wall은 별개다. CPU가 거의 들지 않는 무한 대기를 wall 한도로 종료하고, CPU를 계속 쓰는 코드는 CPU 한도로 종료한다. 준비·큐 대기·컴파일은 실행 타이머 밖이다. 기존 max(2×CPU+1초, CPU+2초) wall 식은 실험용 후보일 뿐 공식 표준이 아니며, 실제 동시성에서 검증한 wall 값을 저장한다.

DOMjudge의 overshoot를 그대로 구현하는 것은 이번 설계의 필수 조건이 아니다. 도입한다면 **공개 판정 한도와 감독자 강제 종료 한도를 따로 기록**하고 판정 여유로 악용하지 않도록 테스트한다.

## 4. 우리 플랫폼의 메모리 정책

시간 배수가 5라고 해서 메모리도 5배로 정하지 않는다. 언어별 자료구조와 런타임 차이는 문제에 따라 다르다.

- 문제별 기본 메모리와 문제·런타임별 덮어쓰기 값을 지원한다. 최종 memory_bytes는 JVM/Node/Python 등 실행 환경을 포함한 전체 제한이다.
- BOJ처럼 기본 메모리 × 계수 + 추가량인 정책도 표현할 수 있게 한다. 이는 초벌 후보 생성 방식이며, 실측 전체 피크와 여유를 확인한 최종 절대값이 우선한다.
- 같은 문제라도 정수 배열과 객체 배열, Python 정수·리스트, Java/Node의 GC 여유 때문에 필요한 양이 달라진다.
- 큰 입력의 **정상 풀이 전체 실행에서 관측한 메모리 피크 + 별도로 기록한 안전 여유**를 출발점으로 확정한다. 측정 피크에 런타임 메모리가 이미 포함되어 있으므로 다시 더하지 않는다.
- 기동만 측정한 최소치도 확인하되, Hello World 메모리만으로 최대 입력의 제한을 정하지 않는다.
- JVM heap/Node old-space만으로 제한을 대체하지 않는다. 네이티브 영역·스택·스레드·자식 프로세스와 참가자가 사용하는 tmpfs도 감독한다.
- Linux cgroup의 메모리 범위와 단위를 명시한다. 프로세스별 RSS를 단순 합산한 값을 전체 사용량으로 취급하지 않는다.
- VM의 큰 가상 주소 예약만 보고 MLE를 만들지 않는다. 메모리 제한의 증거와 실제 OOM 사건을 기록한다.
- AtCoder의 1024MiB나 이전 초안의 256/512MiB를 그대로 기본값으로 확정하지 않는다. 측정 전에는 6개 언어 모두 미확정이다.

| 언어 | 제한 확정 전에 특히 볼 항목 |
| --- | --- |
| C / C++ | 전역·동적 배열, 재귀 스택, 표준 라이브러리 자료구조 |
| B++ | 생성 코드의 메모리 사용, 런타임·배열·문자열 표현 |
| Python | 정수/리스트/큐 객체와 입력 파싱 피크 |
| Java | heap뿐 아니라 metaspace, JIT, 스택·GC 및 네이티브 영역 |
| JavaScript | V8 heap, Buffer, 문자열, 외부 메모리와 파싱 피크 |

## 5. 저장·표시·검증

정책은 언어 이름뿐 아니라 런타임 버전·이미지 digest와 연결한다. 다음 값은 문제 공개 시 대회 스냅샷에, 제출 접수 시 채점 작업에 고정한다.

- 정책 버전, 런타임 ID/버전, 이미지 digest, 테스트 묶음 hash
- 최종 CPU ms / wall ms / 메모리 bytes
- 컴파일 전용 CPU / wall / 메모리 제한
- 출력·PID·임시 공간 제한과 전체 작업 deadline
- 측정 결과, 반복 횟수, 여유를 선택한 이유, 검수 상태

화면에는 선택한 언어의 실제 적용 제한과 전체 언어 표를 표시한다. Java를 선택해도 C++ 기준 2초만 보이는 식으로 표시하지 않는다. 미측정 새 문제는 공개를 막고, 기존 문제는 기존 정책을 보존한다.

언어별 메모리가 달라지면 큐도 슬롯 수만 세어서는 부족하다. 실행/컴파일 작업의 예약 메모리 합과 운영 여유가 호스트 예산을 넘지 않도록 작업을 배치한다. CPU 성능이 다른 워커를 무작위로 섞지 말고 검증한 워커 등급별로 배치한다. 이 부분은 자체 운영 설계이며 특정 서비스의 공개 구현이라고 주장하지 않는다.

검증 대상은 기존 V01–V20에 더해 다음을 포함한다.

- 같은 문제의 언어 변경 시 화면/API/작업 payload/실행기 제한 일치
- CPU 무한 반복과 무한 대기 각각 TLE, VM 기동 성공과 실제 과다 할당 MLE
- CPU/wall/메모리 경계, 자식 프로세스·스레드·tmpfs 포함 범위
- 언어 배수와 문제별 덮어쓰기의 우선순위, 단위·반올림, 미확정 공개 거절
- 제한 변경 중 재시도에 접수 당시 값 유지, 컴파일 산출물 재사용
- 다양한 메모리 예약의 동시 작업에서 호스트 보호와 공정한 큐 진행

## 6. 작업 상태

공식 자료 비교와 기획 수정만 수행했다. 실제 언어별 시간·메모리 측정, 정책 API/실행기 구현, 운영 설정 변경·부하 시험·문제 등록·배포는 하지 않았다. BOJ 원본의 현행 재확인은 남아 있다. BOJ 보존본은 웹 열기 도구에서 실패한 뒤 읽기 전용 HTTP 조회로 언어 표와 예외 안내를 확인했다.
