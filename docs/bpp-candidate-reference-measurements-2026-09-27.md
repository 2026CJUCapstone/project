# B++ 수정 후보 A–J 격리 측정

## 범위

자기 컴파일 고정점과 좁은 회귀를 통과한 후보 `9859a2dc783c9346be2ab9447e1569218bcc5093`의 stage2를 기존 측정 어댑터로 검사한다. **운영 이미지 교체, 새 이미지 빌드, 설치, 운영 DB·큐 사용은 없다.** 이 문서는 후보의 기능/계측 증거이며 최종 설치 이미지 수락과 구분한다.

- 최종 후보 ELF: `7f4864362863ddc9daa687d221387e9f2612220521f89e8a9e05b2e3f40b4a23`.
- 후보 소스 아카이브: `010e9abd3e2469b6bd1b4ee006ed142e695ecf8ee8af0b81b62fac764d2355bf`.
- 기본 실행 이미지: `sha256:7a3aa3717f2c62f60ff52f680335ebee414151136d6f836382b1b543a43c5db1`.
- 기존 이미지의 원본 ELF: `8cd02a03dd9f817bc50a644160dd06b70f4dfe8982abac9f61d6faebcfa9e960`.

패키지 아카이브와 현재 파일은 README만 다르고, 기준 풀이·validator·최대/경계 입력 생성기는 동일하다. 어댑터 아카이브는 현재 출제 검수/재채점/스키마/API 파일 8개와 다르지만, 실행기·정책·런타임 레지스트리·측정 어댑터·Linux supervisor의 바이트는 현재 코드와 동일하다. 따라서 현재 DB 워커 통합 검증으로 해석하지 않는다.

## 컴파일과 실행의 분리

컴파일 컨테이너에만 다음 두 경로를 읽기 전용으로 연결한다.

| 대상 경로 | 입력 |
|---|---|
| `/usr/local/libexec/bpp/v13_stage1` | 검증한 stage2 ELF |
| `/usr/local/share/bpp/src/std` | 같은 고정 소스의 표준 라이브러리 |

원래 컴파일 명령은 바꾸지 않는다. 설치 래퍼는 그대로 사용하며, 일반 제출의 소스 마운트에는 `main.bpp` 하나만 있어 별도 manifest를 주입할 수 없다. 추가 연결 전후에 격리·자원·마운트 조건을 검사한다. 코드 실행 컨테이너에는 후보 컴파일러나 라이브러리를 연결하지 않는다. 해당 컨테이너는 **후보가 만든 프로그램을 기존 이미지에서 실행**하며, 컴파일 뒤 생성물과 각 실행 직전 생성물의 SHA-256이 같아야 한다.

`freshman-candidate`는 일반 `freshman`과 별도 검사 종류다. 기존 설치 이미지 결과 집계기는 후보 보고서를 거절한다. 각 보고서에는 기본 이미지/원본 ELF/래퍼/후보 ELF/소스/표준 라이브러리 지문을 묶은 manifest, 그 해시, 단계별 연결 여부와 생성물 지문을 기록한다. `imageAccepted`는 false다.

## 안전 상한과 해석

- 제어 컨테이너 384 MiB/0.5 CPU, 채점 컨테이너는 한 번에 하나씩 최대 512 MiB/1 CPU.
- 컴파일 CPU 8초/wall 10초, 실행 CPU 5초/wall 10초. 최종 문제 제한이 아닌 기존 진단 상한이다.
- 출력 512 KiB, PID 64, 컴파일 임시 공간 64 MiB, 실행 임시 공간 16 MiB.
- 전체 검사 wall 240초. 네트워크 차단·읽기 전용 루트·권한 제한 유지.
- 숨은 입력마다 새 컨테이너, 문제마다 1회 컴파일. 이전 작업의 컨테이너/파일 정리를 확인한 뒤 다음 문제를 시작한다.
- 제어기는 기존과 같이 Docker 권한이 있는 신뢰된 고정 코드이며, 독립 Docker daemon 보안 경계라는 주장은 하지 않는다.

로컬 집중 검증 **166 PASS /9.53초**. 조작된 후보/라이브러리, 쓰기 가능한 추가 마운트, 과도한 권한, 실행 단계 후보 연결, 생성물 변경, 다른 manifest/컨테이너 이름, 일반 이미지 집계 혼입을 거절한다. 초기 테스트 helper import는 pytest import 방식 때문에 수집 오류가 났으며 명시적 파일 import로 수정했다.

## 실제 1회 결과

**A–J 10문제/31개 입력 모두 AC**. 문제당 1회 컴파일 10개와 입력별 실행 31개, 총 41개의 자식 컨테이너를 순차 실행했다. 제어기 exit 0, 전체 timeout 없음, 모든 단계에서 정상 종료·OOM 없음·프로세스 트리 회수 확인. 마지막 제출 컨테이너와 작업 디렉터리는 각각 0개다.

[원시 보고서](evidence/freshman-reference-bpp-candidate-r1-2026-09-27.json)의 로컬/서버 SHA-256은 `0dcd28e5663902981e111edd918d85ca0901a2ced5e49a35c8380d2029a8acde`다. 후보 manifest는 `9928dfdd646c47132c9e2ade40cde264b33fbdf38e8301c3ca0f2ffc03bb6ddf`로 각 컴파일/실행 기록에 결합했다. 소스·입력·예상 출력·생성물 지문도 원시 기록에 남겼다.

아래는 각 문제의 이번 입력들 중 최대값이다. cgroup 계측에는 supervisor 등 해당 격리 프로세스 비용이 포함된다. CPU와 wall의 측정 범위 차이를 프로그램만의 실행 시간으로 오해하지 않는다. 컴파일 CPU는 문제별 약 1219.831–1436.450 ms였다.

| 문제 | 입력 수 | 실행 CPU ms | 실행 wall ms | 메모리 peak MiB |
|---|---:|---:|---:|---:|
| A | 2 | 4.219 | 2.255 | 8.328 |
| B | 3 | 3.214 | 1.734 | 8.238 |
| C | 2 | 36.193 | 33.278 | 8.332 |
| D | 2 | 25.293 | 13.188 | 8.227 |
| E | 3 | 24.039 | 21.122 | 8.289 |
| F | 2 | 339.660 | 308.693 | 8.805 |
| G | 3 | 4.530 | 2.351 | 8.285 |
| H | 3 | 5.258 | 8.518 | 8.348 |
| I | 3 | 77.996 | 72.163 | 16.098 |
| J | 8 | 18.469 | 15.532 | 8.324 |

이전 이미지에서 G는 3개 입력 모두 CPU TLE, J는 컴파일 오류였다. 기준 풀이와 입력을 바꾸지 않은 이번 후보 검사에서는 해당 입력까지 모두 통과했다. 종전 실패 원시 기록은 보존했다. **운영 이미지가 고쳐졌다는 뜻은 아니며** 운영 pin·설치된 컴파일러는 그대로다.

원시 기록을 내려받아 해시·문제/단계 개수·후보 연결 10회/연결 없는 실행 31회를 확인했다. 소유 경로를 확인하고 서버의 정확한 임시 테스트 복사본 `S4VZhfhi`만 정리했다. 소스/바이너리/원시 증거는 로컬에 보존되어 있다. 기존 basic 서비스 7개 healthy 확인은 단순 상태 검사이며 서비스 전체 수락 검증이 아니다.

정리 중 최초 권한 조정은 제어기가 만든 root 소유 `work/jobs`에서 거절되어 삭제가 실행되지 않았다. 다시 읽기 전용으로 확인한 결과 해당 폴더만 다른 소유자이고 내부는 비어 있었다. 권한 상승 없이 빈 폴더만 제거하는 `rmdir`로 처리한 뒤 검증한 임시 경로를 정리했고 경로 부재·남은 테스트 컨테이너 0개를 확인했다. 이 오류는 채점 실패가 아니며 운영 디렉터리 권한은 변경하지 않았다.

1회 성공은 최종 테스트 전체, 10회 반복, 느린 오답 분리, 정상 동시성, 설치 이미지, DB/워커 재시작 또는 출제 승인을 대신하지 않는다. 다음에는 최종 출제 입력과 복수 기준/느린 풀이를 확정해 반복 측정하고, 승인된 설치 이미지 경로로 다시 검증해야 한다.
