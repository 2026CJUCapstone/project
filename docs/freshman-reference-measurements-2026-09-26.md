# A–J 실제 런타임 측정 — 첫 실행

## 결론

**전체 수락 전이다.** 동일 Linux 이미지에서 언어마다 A–J를 한 번씩 실행했다. C·C++·Python·Java·JavaScript는 10문제와 입력 31개가 모두 AC였다. B++은 8문제가 AC였지만 **G는 CPU TLE, J는 CE**였다. B++ 실패를 제외한 수치를 여섯 언어 전체 통과라고 부르지 않는다.

운영 DB·큐·대회·점수는 건드리지 않았으며 배포, Git push, 이미지 다운로드/빌드, 시스템 설치도 하지 않았다. 사용자 승인 범위의 별도 일회용 컨테이너만 사용했다. 이 검사는 앱의 실제 measured-v1 실행기에 직접 연결한 것이지 API→DB→워커 전체 경로가 아니다.

## 입력·소스·실행 조건

- A–I: 기존 `stress_cases.py`의 최대·경계 descriptor 23개.
- J: 새 `banks_stress_cases.py`의 8개. n=1/2, 중복 누적합, 총합 2의 음수 floor 나머지, ±31999, 최대 n=9999의 양수/총합 1/긴 양수·음수 블록을 포함한다. 최대 블록 정답은 `2665783386674999`다.
- J 기대값은 기존 빠른 풀이를 호출해서 복제하지 않고 닫힌 식으로 작성했다. 블록 식은 작은 m=1..5, p=1..3에서 이차식과 대조했고 BFS는 n≤5, 답≤20만 사용했다. 나머지 빠른 풀이 대조는 독립 oracle이 아닌 회귀 검사로 표시했다.
- 기준 소스는 `tools/freshman_contest/solutions`의 60개 고정 파일이다. 각 원시 행에 소스 hash, 입력·기대값 hash/bytes, 적용 프로필, UTC 실행 시각, compile/case CPU·wall·peak·OOM·출력·정리 결과를 기록했다. 입력 원문이나 다른 사람의 소스를 가져오지 않았다.
- 출제 자료 아카이브 SHA-256: `8dae6743dbf815bb58c310c0111f5c18bf3070508c8cda4fe485862800e633ab`.
- 앱 아카이브 SHA-256: `2e18d203661ac3932f11b965b7ceb0abde190a607a1d27a61bac0b8911e70a68`.
- 런타임 이미지: `sha256:7a3aa3717f2c62f60ff52f680335ebee414151136d6f836382b1b543a43c5db1`. 실제 버전과 감독기 해시는 [기본 판정 검증 기록](judge-runtime-matrix-2026-09-26.md)과 동일하다.
- 호스트: Linux 6.8.0-111-generic, x86_64, 논리 CPU 4개. 운영 daemon에 접근하는 컨트롤러는 검토한 신뢰 코드이며 별도 daemon 보안 경계가 아니다.
- 한 번에 하나의 단계 컨테이너만 실행했다. 컨트롤러 384 MiB/0.5 CPU, 참가자 단계 512 MiB/1 CPU, swap 추가 허용 없음, 네트워크 없음, 읽기 전용 루트다.
- **진단용 상한:** 컴파일 CPU 8초/wall 10초, 실행 CPU 5초/wall 10초, 단계별 출력 512 KiB/PID 64, 컴파일 scratch 64 MiB/실행 scratch 16 MiB. 전체 외부 대기 240초는 보호용 강제 중단 상한이다. 이 값들은 대회 제한으로 확정하거나 관리자 정책으로 등록한 값이 아니다.

## 발견한 B++ 실패

2026-09-27 후속: [G/J 원인 재현과 빌드 차단 회귀](bpp-runtime-regressions-2026-09-27.md)에서 G의 잘못된 스택 예약을 실제 생성 코드로 확인했고 J 오류도 최소 포인터 함수로 재현했다. 아래는 첫 관찰 당시의 기록이다. 컴파일러 수정본의 Linux 통과는 아직 증명되지 않았다.

### G — 세 입력 모두 CPU TLE

단일 값 입력부터 실패했다. 세 CPU 측정은 5,006,581 /5,005,912 /5,003,755 µs이며 한도는 5,000,000 µs였다. 출력은 0 bytes, OOM은 0, exit -9, 트리 회수는 완료됐다. 판정은 잘못된 정답 비교가 아니라 실제 CPU 제한 종료다. 중간 사용자 설명에서 오답이라고 잘못 표현한 것을 원시 기록 확인 후 정정했다.

기준 소스는 1001개 지역 빈도 배열을 초기화·갱신하는 선형/계수 정렬 방식이다. 입력이 작아도 제한에 걸리므로 생성 코드와 지역 배열/반복문 처리를 다음 진단 대상으로 삼는다. 아직 원인을 확정하지 않았고 제한을 늘리거나 다른 풀이로 바꿔 실패를 숨기지 않았다.

### J — 포인터 매개변수 GC 정리 심볼 누락

첫 오류는 `std_mem__bpp_gc_root_slot_remove` 미정의다. 뒤의 NASM label-redef-late 오류들과 분리하여 최초 오류를 보존했다. 컴파일 CPU 2,219,235 µs, 출력 6037 bytes, OOM 0, exit 1이었다. 실행 단계는 시작되지 않았다.

읽기 전용 이미지 메타데이터에서 B++ ref `2d596233f45973394a5d951c40b11f78171c8870`을 확인했다. 별도 Bpp 저장소의 이후 commit `dedc800fdd6586546a467e5446d04d325243706f`는 포인터 매개변수가 필요한 GC 정리 함수를 생성 코드에 남기는 수정과 회귀를 포함한다. J 증상과 일치하는 수정 후보지만 **그 수정으로 새 Linux 실행을 통과했다는 증거는 아직 없다**. 현재 이미지나 컴파일러 ref를 바꾸지 않았다. 별도 Bpp 작업 트리의 사용자 수정도 읽기만 하고 보존했다.

## 도구·로컬 회귀

- `verify_freshman_measurements.py`: 고정 소스/descriptor를 해시로 묶고 한 문제당 compile 1회와 모든 입력의 fresh case 실행을 요구한다. 제한 초과·CE·WA도 원시 보고서에 남기며 정리가 불확실하면 다음 문제를 시작하지 않는다.
- `summarize_freshman_measurements.py`: 중복 반복 번호와 섞인 소스·이미지·입력·측정 도구·호스트·한도를 거절한다. 반복별 case 최대/최소를 계산하지만 별도 cold-start나 정상 동시성 증거를 만들어내지 않는다. 10회 자료가 모두 있어도 정책은 자동 승인하지 않는다.
- 최종 집중 회귀: **250 PASS/34.64초**. J corpus, 측정/집계 도구, 기존 measured adapter와 정책을 포함한다. 집계의 600개 합성 기록 검사는 도구의 반복 수 계산 검사이지 실제 600회 측정이 아니다.

## 전송 장애와 정리

Java 자료 전송 중 연결이 두 번 끊겨 30,829-byte 아카이브가 16,384 bytes만 남았다. 해당 시점에는 채점 컨테이너가 없었다. 디스크·inode·파일 크기 제한을 읽기 전용으로 점검했지만 끊김 원인은 확정하지 못했다. 이미 서버의 Python 테스트 폴더에 있던 동일 해시의 온전한 아카이브를 검증해 해당 테스트 경로로 복사했고 Java 검사를 이어갔다. 다른 자료나 설치로 대체하지 않았다.

여섯 원시 보고서를 로컬에 보존한 뒤 각 실제 경로·크기를 확인하고 `yLVQkAxk`, `974xTGhu`, `5xEXcQBU`, `bpZCBnq1`, `2aZmikqU`, `AQ0caLD5`의 테스트 복사본만 제거했다. 이후 경로 부재, 테스트 컨테이너 0개, 기존 basic 서비스 7개 healthy를 확인했다. 로컬 소스·아카이브·원시 보고서는 남아 있어 테스트 복사본을 재생성할 수 있다.

2. 최종 입력 묶음·여러 정상 풀이·느린 풀이를 고정하고 문제×언어 최소 10회 및 기동/반복/정상 동시성 조건을 구분해 측정한다.
3. 안전 여유를 근거와 함께 정한 뒤 정책 버전과 측정 근거를 관리자 검수에 연결한다. 이번 진단 상한을 그대로 승인값으로 쓰지 않는다.
4. 실제 PostgreSQL/워커 재시작/예산·부모 OOM·V01–V20/C01–C12의 나머지 조건과 출처·난이도·일정·J 배점/공개 정책 승인까지 확인한다.
