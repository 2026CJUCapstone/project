# 채점 작업 자원 예약 — 구현 및 검증 기록

작성일: 2026-09-26. 상태: 로컬 구현·회귀 검증, 운영 미적용.

## 적용 범위

기존 실행 슬롯 수 제한에 메모리·CPU 배정량 검사를 추가했다. API가 사용하는 실행 큐에 연결되며, 일반 IDE 실행·터미널·일반 문제·대회 제출이 같은 예약 집계에 들어간다. 실제 cgroup 제한을 대신하는 기능은 아니다.

- DB 잠금 안에서 작업 선택과 예약 저장을 함께 처리한다. 여러 워커가 동시에 가져가도 예산을 각각 따로 계산하지 않는다.
- 측정 정책의 예약 메모리는 `max(컴파일 메모리, 실행 메모리) + 저장 참조 버퍼 예약 + 작업별 외부 여유분`이다. 저장 참조가 없으면 버퍼 예약은 0이며, 있으면 `12 × 최대 케이스(입력+정답 bytes) + 131072`다. 영수증 고정값과 실제 manifest에서 재계산한 값이 같아야 한다. 두 단계는 순차 실행이므로 합산하지 않는다. tmpfs는 이미 cgroup 메모리에 포함되므로 다시 더하지 않는다.
- 버퍼 예약은 한 케이스 복원 중 압축/원본/UTF-8 복사를 위한 보수적 계산이다. 실제 최악의 워커 RSS 검증은 남아 있다. 컨테이너의 실행 메모리 제한은 이 외부 버퍼 값 때문에 커지지 않는다.
- 측정 작업은 1,000 millicpu를 예약한다. 이것은 동시 CPU 배정량이며, 제출의 누적 CPU 시간 제한과는 다르다. 실제 감독 실행기도 같은 배정량을 적용해야 한다.
- 기존 정책 제출은 접수 당시 저장한 메모리·CPU 배정량을 사용한다. 정책 없는 IDE 작업은 현재 기존 샌드박스 설정으로 예약한다.
- 측정 정책의 공개·접수 최대 메모리도 호스트 예산에서 외부 여유분을 뺀 값으로 검사한다. 기존 문제의 절대 제한값은 바꾸지 않는다.
- 측정 작업은 지정된 워커 등급에서만 선택한다. 다른 등급의 작업은 건너뛰지만, 같은 등급의 먼저 접수된 작업이 남은 자원에 들어가지 않으면 뒤의 작은 작업을 먼저 처리하지 않는다.

## 장애·이전 버전 처리

`running` 상태의 예약만 집계한다. lease가 만료되었다는 이유만으로 반환하지 않는다. Docker 요청 결과가 불명확하거나 컨테이너 정리가 확인되지 않은 작업도 계속 예약한다. 기존 정리·완료 트랜잭션을 통과한 뒤에야 반환된다. 중복 완료 요청이나 이전 lease의 결과는 반환을 중복 처리하지 못한다.

마이그레이션 v13은 실행 기록에 nullable `resource_reservation`을 추가하고, 별도 예산 테이블을 만든다. 기존 실행·결과·정책·schema marker는 유지한다. 예약 없는 이전 버전의 실행 중 작업을 만나면 자원량을 추측하지 않고 새 작업 선택을 멈춘다.

예산은 Docker daemon ID별로 DB에 고정한다. 같은 daemon을 사용하는 워커의 설정이 달라지면 실패로 처리한다. daemon에 묶이지 않은 레거시 실행은 어느 호스트에 있는지 알 수 없으므로 모든 예산에서 보수적으로 차감한다. 잘못된 scope·타입·버전의 실행 중 예약도 무시하지 않고 작업 선택을 중단한다.

## 운영자가 정해야 할 값과 제약

| 설정 | 의미 |
| --- | --- |
| `EXECUTION_MEMORY_BUDGET_MB` | 해당 Docker daemon의 전체 작업 예약 메모리 상한. 단위는 MiB |
| `EXECUTION_CPU_BUDGET_MILLIS` | 전체 동시 CPU 배정 상한. 1,000은 1 CPU |
| `EXECUTION_JOB_OVERHEAD_MB` | 컨테이너 바깥 작업 처리 여유분. 작업마다 추가 예약 |
| `JUDGE_WORKER_CLASS` | 실제 성능 측정에 사용한 워커 등급 |

예제의 1,024MiB/2,000millicpu/32MiB는 설정 예시이며, 운영 서버 실측·안전성 인증 값이 아니다. 운영 서비스·DB·OS의 여유를 먼저 제외하고 확정해야 한다. 예산 변경은 전체 해당 작업을 drain한 뒤 별도 승인된 운영 절차로 해야 하며, 코드가 DB 상한을 자동으로 올리지 않는다. 변경용 관리 도구는 아직 없다.

현재 자원 구역은 **호스트당 하나의 Docker daemon**을 전제로 한다. 동일 물리 호스트의 여러 daemon은 자동으로 한 예산에 합쳐지지 않는다. 그 구성에는 별도 물리 호스트 자원 구역 매핑이 필요하다. 다른 성능의 호스트에 같은 등급 이름을 붙여도 성능을 자동 검증해 주지 않는다.

이전 바이너리와 새 바이너리의 혼합 운영은 지원한다고 검증하지 않았다. 이전 워커는 예약을 기록하지 않으므로 도입 시 기존 워커 전체 drain과 스키마 확인이 선행되어야 한다. 글로벌 동시 슬롯 수 제한도 그대로 남아 있다.

## 검증과 미검증 구분

`backend/tests/test_execution_resource_budget.py`에서 동시 claim 경쟁, 메모리/CPU 각각의 상한, 단계별 최대값·외부 여유분, 같은 등급 FIFO, 다른 등급 제외, 여러 daemon, 레거시 보수적 집계, 재시작, 만료된 lease, 불명확한 Docker 작업, 이전 토큰, 잘못된 저장 값, 설정 불일치, 초과 예약, v12→v13 반복 마이그레이션을 검증한다.

관련 큐·워커·대회·정책·마이그레이션 묶음은 트랜잭션 실패 검증 추가 후 **79 PASS / 39 PostgreSQL 환경 skip**이다. SQLite 경쟁 테스트는 실제 PostgreSQL 잠금 검증을 대신하지 않는다. 전체 회귀 결과는 구현 매트릭스의 최신 행을 기준으로 한다.

처음 작성한 두 테스트에서 JSON boolean과 숫자의 Python 동등 비교 때문에 오염 값이 저장되지 않는 문제, 같은 접수 시각의 UUID 순서를 가정한 문제가 드러났다. 테스트 데이터의 DB 쓰기를 명시하고 접수 시각을 분리한 뒤 다시 검증했다. 제품의 정렬 규칙이나 엄격한 타입 검사를 완화하지 않았다.

아직 남은 필수 조건은 실제 감독 실행기, 컴파일 산출물 1회 생성·케이스별 격리, 최종 cgroup 계측, 승인된 등급·런타임 연결, PostgreSQL 및 실제 Linux 혼합 메모리 작업의 자원 상한 검증이다. `measured-v1` 실행은 기존 실행기에 잘못 흘려보내지 않도록 여전히 거부한다. 운영 대회 등록·배포·Git push는 수행하지 않았다.
